**Version**: v0.1.0
**Slug**: milestone-android-app
**Filename**: docs/releases/v0/v0.1/plans/v0.1.0-milestone-android-app.md

**Created**: 2026-11-06
**Goal**: On an Android phone, a sideloaded MileStone APK lets the user add any of the 14 catalog programs by logging in through an embedded browser (including 2FA) or by typing a balance, shows each balance on a reorderable dashboard, refreshes connected programs when the app comes to the foreground, and marks a tile "Reconnect" when its session has expired; the eight priority programs (Amex, Chase, Delta, Alaska, Aeroplan, Marriott, Hyatt, Hilton) refresh automatically.

## Overview

MileStone is a native Android app, written in Kotlin with Jetpack Compose and Material 3, that puts credit card, airline, and hotel loyalty balances on one dashboard. The user adds a program from a searchable catalog of 14 programs. For a program the app can read, it opens that program's own login page in an embedded `WebView`, the user signs in there (2FA included), and a small injected script reads the points balance from the account page and hands it back to Kotlin. The app never sees or stores a password; the session lives only in that program's own WebView cookie profile inside the app's private storage. For a program the app cannot read, the user types the balance.

Delivery for v0.1.0 is a signed APK installed on the user's own device. There is no Play Store listing, server, or account system. Balances, balance history, timestamps, sort order, and session metadata live on the device in Room and a Tink-encrypted DataStore. When the app comes to the foreground, it refreshes each connected program that was not attempted in the last 5 minutes, using an invisible `WebView` that reuses the saved session. Pull-to-refresh, a "Refresh All" button, and a per-tile retry cover manual refresh. When a session has expired, the tile shows "Reconnect", and tapping it reopens the login sheet.

Scraping is fragile. Delta, United, and American Airlines have forced AwardWallet to stop reading their accounts, Amex often challenges automated sessions with a security code, and card issuers commonly end sessions after 10 to 30 minutes of inactivity. The plan therefore measures feasibility on a real phone in Phase 2 before building the login and sync machinery, ships a working manual-entry app in Phase 4 before any scraping exists, and treats each extractor as data that is verified program by program within a fixed timebox. For card issuers with short sessions, "Reconnect" on reopening is an expected state, not a defect.

## Definition of Done

Each step is run by the user on the phone with the signed release APK, and each has one observable result.

| # | User action | Expected on-screen result |
|---|---|---|
| 1 | Install the signed release APK with `adb install -r` and open it | The MileStone launcher icon appears; the app opens on an empty dashboard that explains how to add a program |
| 2 | Add a priority program from the catalog with "Sign in to sync" and complete its 2FA | The login sheet closes by itself, a snackbar names the program and its balance, and a tile shows that balance and "Last updated: just now" |
| 3 | Add a program with "Enter balance manually" | A tile shows the typed balance and a "Manual" label |
| 4 | Switch the sort menu to Custom, long-press a tile, and drag it to the top; force-stop and reopen the app | The dragged tile stays at the top after reopening |
| 5 | Leave the app for more than 5 minutes, then reopen it | Connected tiles show a spinner, then a new "Last updated" time (or "Reconnect" for a program whose session expired) |
| 6 | Choose "Sign out" from a connected tile's menu | The tile shows the "Reconnect" chip; tapping it opens that program's login sheet |

## Non-Goals

- Automatic sync for Capital One, Citi, Bilt, United, American AAdvantage, and British Airways is attempted within the extractor timebox but is not required for v0.1.0; any of them may ship as manual-only with a known-gap entry.
- No aggregator integration (Plaid, AwardWallet) and no aggregator stub; recorded as future work.
- No remote logos and no image-loading library; program logos are bundled drawables shipped inside the APK, with a monogram badge as the fallback.
- One account per program; a second login for the same program is out of scope because each program has one cookie profile.
- No Play Store distribution, server, cloud backup, or device-to-device transfer.
- Programs whose only sign-in path is Google or Apple identity are manual-only, because those providers reject embedded browsers.

## Architecture Summary

One Gradle module, `:app`, with package boundaries enforcing Clean Architecture. A multi-module split is deferred until there is a second consumer.

| Package | Holds | Depends on |
|---|---|---|
| `com.bendourthe.milestone.domain` | `Program`, `ExtractionSpec`, `LoyaltyAccount`, `SyncResult`, `FailureReason`, `SortMode`, repository interfaces, use cases | nothing Android-specific |
| `com.bendourthe.milestone.data` | Room database and DAOs, static `CatalogRepository`, `TinkSessionStore`, `SettingsStore`, repository implementations | `domain` |
| `com.bendourthe.milestone.sync` | `WebViewConfig`, `HostPolicy`, extraction script and parser, `LoginBridge`, `HeadlessWebViewBalanceSource`, `WebViewHost` port, `SyncManager` | `domain`, `data` |
| `com.bendourthe.milestone.ui` | Compose screens, ViewModels, theme, navigation; `MainActivity` implements `WebViewHost` | `domain`; reaches `data` and `sync` only through `AppContainer` |

Dependency injection is a hand-written `AppContainer` created in `MileStoneApplication`. `SyncManager` is the single writer of scraped balances: the interactive login and the headless refresh both deliver results through it.

## Extractor Phases 7 to 9: Shared Procedure

Phases 7, 8, and 9 each cover one batch of programs and follow the same procedure. Each pauses for one capture session; an unattended run stops at the capture sub-task with numbered steps printed.

- **Scope per program**: only programs with verdict `AUTOMATIC` in the feasibility record, plus any priority program chosen for an attempt anyway. `MANUAL_ONLY` programs are skipped and already have a manual path.
- **Timebox**: one capture attempt per program and 45 minutes of selector work per program. When either runs out, the program becomes `ManualOnly(reason)` in the catalog and gets a known-gap entry in `docs/releases/v0/v0.1/known-gaps.md` (source phase, reason, next step). For a priority program, the agent stops and asks a maintainer whether to accept manual-only or extend the timebox, and records the answer.
- **Capture**: a maintainer installs the `capture` build, signs in to each program, opens the balance page, taps "Capture page", and runs `adb shell run-as com.bendourthe.milestone.capture cat files/captures/<programId>.html > app\src\test\resources\fixtures-private\<programId>.html` for each file. No balance is typed: a private capture is checked for exactly one balance match that parses, and only synthetic fixtures carry an exact `.expected` value (decision). Afterward the maintainer clears the capture build's data and uninstalls it.
- **Selectors**: the narrowest stable selector (prefer `data-*` attributes or ARIA labels over generated class names), plus `loggedInUrlPattern` and `loginUrlPattern` matching the URLs observed. A balance that exists only inside a closed shadow root, a canvas, or an image becomes manual-only rather than a fragile workaround.
- **Committed fixture**: a hand-written synthetic file `app/src/test/resources/fixtures/<programId>.html` that copies only the balance element's ancestor chain and attributes with a fake balance, so CI exercises the selector without any real data.
- **Tests**: the parameterized `ExtractorFixtureTest` runs each selector with Jsoup (`select` or `selectXpath`) against both fixtures when present, asserting exactly one match and a `BalanceParser` result equal to the expected value. A missing private fixture is reported as a visible skip naming the program, never as a pass.
