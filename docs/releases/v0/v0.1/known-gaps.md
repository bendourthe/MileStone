| G05 | Delta SkyMiles needed a sync approach other than manual entry, which was rejected as a decision. Its page went blank after sign-in. Root cause found for United (G06): MileStone's WebViews laid pages out with a zero viewport height, so every `vh` length was 0. Fixed in `WebViewConfig` (commit 11ee7d6). Signing in over Site check then showed that Delta asks for a personal or business account and afterward shows its home page with the miles in the header, and the catalog now reads them (`DELTA_XPATH`, synthetic fixture `delta.html`). The first Add program attempt timed out because the hidden browser stayed on the signed-out home page, which shows no form; a headless session with a saved sign-in now opens the program's sign-in page once when its balance page times out signed out. The hidden sign-in then reached the personal or business choice and stopped there (a page with 5 buttons and no fields); after Personal was chosen in the sign-in window, Delta read its miles on every refresh. The hidden sign-in now presses Personal when a page offers Personal and Business. A later remove and re-add of Delta still ended in the sign-in window after 2 to 3 minutes of hidden sign-in, and the stop reason was lost because the phone's log had rotated; since then MileStone keeps its own diagnostics file (hosts, page shapes, stop reasons only). Its first record: the hidden sign-in submitted, landed on a page with 5 buttons and no fields, and waited 2 minutes before stopping as unfinished; the in-run retry then read the miles in 3 s, so the sign-in had worked. Since commit c36d18e, a page after the password that asks for nothing opens the balance page once (unit test in `AutoSignInSessionTest`). Delta's session ends within about 30 minutes, so every keep-alive after that lands signed out; since the quiet keep-alive clarification of [ADR-0005](../../../decisions/0005-sign-in-only-on-open-with-stop-reasons.md), those misses leave the tile unchanged. A manual Refresh took about 98 s; a hidden sign-in now starts at Delta's sign-in page and skips the session read once a read has found the session ended (same ADR, faster sign-in clarification). | One Add program sign-in that finishes without anyone using the phone. | Feasibility record |
| G06 | United MileagePlus does not sync yet. The empty sign-in had one cause: `100vh` measured 0 px in MileStone's WebViews (emulator), collapsing United's sign-in panel. Fixed in commit 11ee7d6; the panel now renders, and the catalog opens `/en/us/myunited`, which shows sign-in by itself (the old address was a 404 page). Signing in over Site check (MileagePlus number, password, texted code) showed the number under the MILES heading, and the catalog now reads it (`UNITED_CSS`, synthetic fixture `united.html`). A later remove and re-add still opened the sign-in window. A texted-code box named only by its label (no code-like name or autocomplete) was not recognized; the page script now reads field labels (instrumented fixture `code-by-label.html`), unconfirmed on the live site. The diagnostics file shows the hidden sign-in filling the username, then the password, then stopping on a page with 6 text boxes, no box marked as a code, a "remember this device" checkbox, and text-message wording; United most likely splits the code into one box per digit. Since commit c36d18e the page script types a code into 4 to 8 single-character boxes (instrumented fixture `code-by-digits.html`), and a stop logs each text box's type, autocomplete token, length limit, and input mode. | One Add program sign-in and one balance read on a device, or the diagnostics file of the next attempt. | Feasibility record |
| G17 | Amex and Capital One stopped as `Password refused` although the saved sign-in worked from the tile menu, and their menus offered no Refresh. Any password form seen after submit counted as refused. Now only a visible site error counts; a form back with no error is unfinished and may be retried, Refresh shows on every syncing tile, and Refresh clears a paused sign-in ([ADR-0005](../../../decisions/0005-sign-in-only-on-open-with-stop-reasons.md), clarification). Why their hidden sign-in leaves the form on screen is not yet known. Capital One stopped as refused again with the same shape (username and password typed, form up about 16 s later, one checkbox, six buttons, no code box, no HTTP error after submit). Since then only an on-screen marker that appeared or changed after typing counts as a refusal, and each stop logs error-marker counts ([ADR-0005](../../../decisions/0005-sign-in-only-on-open-with-stop-reasons.md), error-marker clarification; fixtures `standing-notice-signin.html` and `refused-in-standing-notice.html`). Refresh on the Capital One tile was confirmed on a device to reconnect it with that build. A later global refresh stopped Capital One as refused again, with no message and one non-password box marked invalid; such a box no longer counts as a refusal (ADR-0005, Capital One username clarification), but why Capital One rejects the typed username is unknown. | One Amex stop or success with this build; one Capital One global refresh with the build that ignores a username marked invalid. | ADR-0005 |
| G16 | World of Hyatt's automatic sign-in is judged refused after filling only the password. One attempt logged no HTTP error after submit, so Hyatt rejected nothing: the page found no username box, and a password box was still showing afterward. On the emulator Hyatt serves a bot-protection challenge page (two scripts and an iframe, matching Kasada), so its form can be inspected only on a physical device. Since commit 07a88b2, a stop like this opens the site instead of asking for the password again. Later attempts met a page with one password box and two buttons; the fill pressed the form's first button, which can be a typeless show-password toggle, so the submit now prefers a Sign in style label and skips reveal toggles (fixture `identity-first.html` proves it). The real flow was then found: Hyatt's email step emails a sign-in link that cannot open in MileStone, and its "Sign in with password" choice, which is not a button or a link with an address, leads to email, password, and last name; signing in by hand that way succeeded. The route search now covers any visible element labeled exactly as the route (fixture `password-route.html` proves it). After a manual sign-in, a refresh on opening reads the balance, but every background keep-alive refresh is sent to `world.hyatt.com`, which is outside Hyatt's allowed hosts, then times out on a near-empty `www.hyatt.com` page. | Confirm the next automatic Hyatt sign-in on a device; find why only the background refresh is sent to `world.hyatt.com` before deciding whether that host belongs in the feasibility record. | Phase 9 |
