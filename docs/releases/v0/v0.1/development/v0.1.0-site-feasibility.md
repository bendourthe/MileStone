## Notes

- amex: the default browser or the Amex app would be the expected sign-in route; the embedded WebView is a separate browser, so Amex treated it as a new device and asked for approval in the Amex app. Expected once per program, since the program's WebView profile keeps its cookies.
- amex: after the app was reinstalled and restarted (data kept), Site check opened signed out. This suggests the Amex sign-in cookie lasts only until the WebView process ends, which would mean "Reconnect" on most app opens. Session 2 confirms or rules this out.
- amex: the Rewards section of the overview page can also list co-brand airline and hotel balances. Recorded as a possible later source for `delta` and `hilton`; v0.1.0 still reads each program from its own site.
- Sign-in approach (decision): sign-in through the default browser or the program's own app was considered. Neither can be read by MileStone, so the embedded WebView stays the only sync path, and every tile gains an "Open in app or browser" action for viewing the account. See [ADR 0002](../../../../decisions/0002-open-in-app-or-browser.md).
- hyatt: an email sign-in link opens wherever Android sends `www.hyatt.com` links, which is the default browser, so the session lands outside MileStone's WebView profile. Copying the link and using "Paste link" (Site check) or "Paste sign-in link" (sign-in screen) keeps the session inside the program's WebView profile.
- delta, diagnosis over the debug inspector: `https://www.delta.com/login/loginPage` redirects to `/skymiles/profilePickerPage`; the document returns HTTP 200 and the `idp-root` app renders only its header and footer, with all nine form inputs hidden and the bot-protection overlay `#sec-overlay` not displayed. The WebView reports client-hint brands `Android WebView 156` while the user agent claims Chrome; overriding both to a consistent Chrome identity for one load did not change the result, so the mismatch is not the sole cause.
- delta (sign-in over the debug Site check, masked structure over the debug inspector): after sign-in Delta asks for a personal or business account, then shows the home page `www.delta.com/` with the miles in the header. The balance is the `span` containing "miles" inside `div#mach-core-login-flyout-name-container` (button `#mach-core-login-flyout-details`, element `idp-login`); its sibling `span` is the member name. Page resources load from `www.delta.com`, `signin.delta.com`, `tms.delta.com`, `smetrics.delta.com`, `catalog-api-prd.delta.com`, and `pulse.delta.com`; only `www.delta.com` and `signin.delta.com` are allowed for navigation.
- united (sign-in over the debug Site check, masked structure over the debug inspector): the sign-in takes the MileagePlus number, Next, the password with Remember me ticked, a texted code, and the remember this device box, and reaches `www.united.com/en/us/myunited`. The balance is the `span` inside the `div` whose class starts `...MileageBalance__totalMiles` under the MILES heading; the header greeting and the recent activity rows also show miles. The page has no referrer and loads resources from `www.united.com`, `media.united.com`, and a survey host, so the whole sign-in stayed on `www.united.com`.
- marriott (over the debug Site check): sign-in worked and the home page loaded with an advertising pop-up over it; pages after sign-in now load, so the earlier failure was the zero-viewport-height bug.
- marriott (masked structure read through the debug inspector): the signed-in home page is `https://www.marriott.com/default.mi` on host `www.marriott.com` only. The points are an `h4[data-testid=points]` in the `[role=dialog][aria-labelledby=account-panel-label]` account panel, opened by `button[data-testid=common-static-SignInDrawer]` at the header's top right. Marriott is now AUTOMATIC, with that button pressed once when the points are not shown.
- Repeat sign-in: amex, chase, capitalone, alaska, aeroplan, hyatt, and hilton signed in. delta: after signing in, a blank page (Session 1 never reached the form, so the form now renders). united: tapping the sign-in buttons does nothing. marriott: after signing in, the account menu cannot be opened. hyatt: the first link (`/profile/sign-in`) showed "page cannot be found" because the corrected account-overview link was not yet installed.
- Session 2, after swiping Site check away and reopening it: alaska and aeroplan opened signed in; amex, chase, capitalone, hyatt, and hilton asked for sign-in again. Hilton was checked short of the full hour. Because the five were lost on a process restart well inside an hour, the likely cause is sign-in cookies that end with the browser session rather than an inactivity timeout; the plan treats "Reconnect" on reopening as an expected state for such programs.
- `hyatt` host: Copy hosts output after the pasted-link sign-in: `page: https://www.hyatt.com/profile/en-US/account-overview`, `hosts: www.hyatt.com`.
- `hyatt` host `world.hyatt.com`: the signed-in account overview navigated the main frame to it in MileStone's refresh (phone log "hyatt headless navigation blocked to world.hyatt.com", repeated across refreshes), after which the refresh timed out; added so the redirect can complete.
- `login.aircanada.com`, `auth.api-gw.dbaas.aircanada.com`, and `akamai-gw.dbaas.aircanada.com` are Air Canada's own sign-in hosts, so they are first-party `allowedHosts`, not identity providers. The same holds for `auth0.alaskaair.com` and `verified.capitalone.com`.

## Session Lifetime

|---|---|---|---|
| alaska | yes | yes | stays connected with ordinary refreshes |
| aeroplan | yes | no | needs the keep-alive refresh or automatic sign-in ([ADR-0004](../../../../decisions/0004-keep-alive-and-automatic-sign-in.md)) |

Verdicts stay AUTOMATIC: every program with a reachable balance page can be read after a sign-in, and automatic sign-in plus the keep-alive refresh cover the short sessions.
