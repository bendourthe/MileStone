Date: 2026-11-21 (America/Los_Angeles)

Adoption target: v0.8.0

Target confirmation: The owner selected v0.8.0 in this session, after the existing v0.6 offers and v0.7 grouping plans. Changes proposed to those existing plans remain advisory and require separate approval.

Baseline: MileStone `develop` at `bc177ebf0ca6442660ef58372441f98db82eb527`, with v0.5.0 recorded in CHANGELOG.md. The queue enumerator found v0.6.0 merchant-offers (draft, 19 open tasks) and v0.7.0 benefits-category-grouping (planned, 19 open tasks), with no unreadable plans. ## Findings

MileStone should build on its existing product definitions, exact card identities, local issuer sessions and Search. The largest new capability is a maintained product-and-earning-rule library, followed by an explainable purchase recommendation that combines earning rules with confirmed card-specific offers. Offer discovery and adding already belong to v0.6; their implementation should not be duplicated in v0.8.

The public CLI is a client of a hosted MCP service. It exposes useful input and output contracts, but contains neither the full card library nor the recommendation engine. The downloadable extension supplies stronger implementation evidence: separate issuer adapters discover account cards, retrieve offers, submit enrollment requests in the signed-in browser context and synchronize data to CardPointers. This supports an independent local design, not copying its code, importing its database or treating its bank endpoints as a supported API.

The most consequential finding is current Amex behavior. CardPointers' help page, updated September 4, 2026, says its former multiple-card technique stopped working for most users after an August change. Its replacement selects a card by category or manual priority. The inspected extension still exposes an experimental all-cards choice. Neither source establishes issuer permission or eligibility for MileStone. Preserve the owner's policy of adding every independently eligible offer on every eligible card, verify restrictions on the actual account, and leave unresolved cases pending. Do not silently replace that policy with preferred-card selection. [S3, S9]

## Source Security Scan

Verdict: **PROCEED-WITH-CAUTION**.

Before content inventory, the repository and initial HTML were downloaded into a temporary directory and scanned for instruction override phrases, agent-directed text, destructive commands, execution and install hooks. Additional first-party pages were downloaded and scanned before their detailed reading. Before extension content inspection, its archive paths and textual JS/HTML/JSON members were scanned. ## Extension Mechanics

All observations in this section are from S9's exact package. Method names are source anchors in its minified `content/content.js`; they are not instructions to invoke bank services. Full implementation files are retained only in the temporary research cache, not vendored into MileStone.

1. **Session context**: manifest.json declares storage, unlimitedStorage, activeTab and scripting, plus HTTP/HTTPS access to all hosts and a content script at document_end. It operates inside an authenticated browsing environment. Avoiding password sharing does not eliminate access to session-authorized bank data.
2. **Account discovery**: products.js looks for Amex products in Bootstrapper.digitalData.products, window.digitalData.products or window.a_digitalData.products and saves them in page localStorage. This file is account-product extraction, not a bundled global library of 5,000 cards. `loadAmexBankCards` and Chase setup methods discover reachable cards.
3. **Issuer adapters**: `loadAmexBankCards`, `addOfferAmex`, `addOfferChaseNew`/`addOfferChaseOld` and Citi-specific methods demonstrate independent issuer paths. Chase code contains both newer marketing-offer and older Cardlytics route families. Amex contains multiple request/response generations, including method names labeled 2026 and 2027. Those labels do not establish future issuer support.
4. **Read/action split**: Amex paths separately request eligible/enrolled lists and enrollment; session requests use `credentials: "include"`. Chase paths carry account/offer interaction context. This is evidence of session-bound HTTP integration rather than only DOM button clicking. Android WebView origin/cookie/CORS behavior must be evaluated independently; browser-extension capabilities do not automatically transfer.
5. **Normalized offers**: issuer adapters produce fields such as minimum spend, percentage/maximum discount, bonus points, repeatability, terms and exact external card/offer IDs. MileStone needs equivalent meanings in its own model, with private IDs kept local and public fixtures synthetic.
6. **Selection and recovery**: the bundle includes `getPrioritizedAmexOffers`, `rankAmexOfferCards`, an enrollment queue and category/manual/all-cards modes. Multiple endpoint generations are a maintenance warning. Do not copy fallback behavior that can resend an uncertain action. Re-read the exact card/offer state before any retry.
7. **Success checks**: some Amex branches inspect isEnrolled or a success-purpose field; an older branch also accepts HTTP success. MileStone's stronger contract must require issuer confirmation bound to the exact card and offer. An HTTP 200 or a local notification alone is insufficient.
8. **Vendor synchronization**: content/background code builds authenticated x.cardpointers.com API requests; background code includes token refresh. The bundle also contains an ui-api.tripleup.dev SAML-processing URL, whose use and data handling were not established. Do not infer that all information stays on-device from the no-bank-password claim. MileStone should implement its core locally without these destinations.

Remaining unknowns: live account completeness, pagination behavior across issuer variants, valid current enrollment authority, actual production server ranking/data sources, and the full extension permission/data-flow audit. This research does not establish source GO for live issuer actions.

## Library Design

Extend the local product concept in place before introducing infrastructure. Separate three meanings: a public product template, an owned card instance and issuer-observed state. A product may apply to many owned cards; personalized offers and benefits belong to the exact owned instance. A bank sign-in is a connection, not a product or a household profile.

Proposed first implementation locations are `domain/CardProducts.kt` plus a focused `domain/RewardRules.kt`, a local `data/catalog/` loader only if a bundled data file is warranted, and their existing test packages. Keep program hosts/capabilities in StaticCatalogRepository. Decide whether the 70 records remain Kotlin or move to a bundled structured file after the rule schema is proven; no catalog server or new runtime dependency is justified yet.

Required fields: stable product ID, issuer and country, segment, currency, reward program/unit, aliases/legacy variants, base earning rate, category rules, caps and cap periods, exclusions, activation requirements, effective dates, source URL, last verification date and confidence. A product with unsupported or expired earning data can still be shown but cannot supply a confident winner. Preserve per-card user overrides separately from publisher defaults.

Start with documented earning rules for a small representative subset of the existing Chase/Amex products, then expand through a stated coverage matrix. Source facts from issuer-owned public terms and version each reviewed change. Do not claim all 70 products have verified rules merely because they have artwork. Broader US/Canada/international coverage follows verified data, not a target count. Missing-card manual entry should remain usable offline, label user-entered rules and support later product matching without changing CardKey or sign-in bindings.

Maintenance acceptance: validate unique IDs, units/currencies, rule dates, cap periods and source metadata; review changed rules before bundling them; retain the previous valid catalog on an invalid update; expose stale/unsupported coverage. CardPointers demonstrates manual submissions and review [S5], but the source of its full database and redistribution rights are not public in the inspected sources.

## Purchase Recommendation

Reuse the existing top Search entry point. Preserve its accepted added-program/stored-data results and exact Back behavior. Add an explicit purchase-recommendation action or mode with merchant/category, amount and currency, and an explanation of the eligible owned-card scope. Product discovery belongs in a separate library picker; it must not silently broaden ordinary Search to cards the owner does not hold.

The calculation is deterministic and local. S4 documents multiplier times point value as CardPointers' base ordering. MileStone should use that understandable foundation with explicit offer eligibility and spending conditions:

`estimated incremental value = base/category reward value + applicable offer value - known incremental fees`.

Use integer minor units or decimal-safe arithmetic and consistent point units. Apply category caps by splitting the purchase between remaining bonus capacity and base rate. Do not add base and category rates twice when the category rate already represents total earnings. Percentage offers need minimum spend, remaining redemption cap and repeatability; fixed credits require their actual threshold conditions. Do not stack offers/credits unless their terms allow it. Welcome-bonus goals can be a separately chosen objective, not an unconditional bonus on every purchase.

Synthetic example, not current issuer terms: for a $100 purchase, card A earns 3 points per dollar valued by the user at 1.5 cents, or $4.50. Card B earns 2% cash back plus a confirmed available $10 credit after $75 spend, or $12. Card B wins only when the exact card, merchant/channel, date, prior-redemption state and threshold qualify. If the offer is merely discovered, display conditional value separately and do not count it as confirmed savings. Below $75 the fixed credit contributes zero.

Merchant matching must distinguish a merchant-name guess from issuer category coding, online versus in-store, geography, merchant subsidiaries and payment intermediaries. Unknown category or cap usage produces a visible assumption, bounded scenarios or a request for context, rather than a guaranteed best card. Unknown point value cannot be compared with cash as though points equal currency. Support user valuations and show which assumptions reverse the ranking; do not promote CardPointers' example valuation into a universal financial fact.

The result should expose the rule source/date, base and offer components, eligibility/activation state, uncertainty, tie-break and exact card route. Card ordering may break true ties but must not silently authorize preferred-card offer enrollment. Browsing or calculating recommendations must perform no issuer mutation. Tests must include threshold boundaries, currency mismatch, exhausted/unknown caps, expired/unadded/redeemed offers, duplicate product instances, equal endings, merchant aliases, stacking restrictions and deterministic ties. Exercise the actual built Search flow and preserve its existing measured latency contract separately from any new recommendation-workload measurement.

## Risks and Conflicts

Product-rule data can become stale faster than artwork. Dates, source citations, coverage and explicit unknowns are required. Public issuer terms may differ by region, legacy product, channel or account; a high multiplier is not a guarantee for a merchant. User-entered valuations and unknown cap usage must remain visible.

New manual cards conflict with the current connected-only Add program contract if inserted into it without distinction. Resolve through a separate card library workflow and owned-card reconciliation design. Data migrations and existing connected-card identity are the main local risks. Library coverage never changes network allowlists.

Issuer actions are the highest risk. Availability on several cards, identical wording and the existence of an Add button do not prove independent eligibility or automation authorization. Public CardPointers code is not a supported bank API. Do not copy legacy endpoint fallbacks, session exfiltration, broad host permissions or permissive success tests.
