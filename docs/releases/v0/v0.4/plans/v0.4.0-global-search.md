**Goal**: Let the owner find a stored program, card, or benefit from a top search icon, see matches grouped by program, open the correct item, and return without losing context, entirely on the device and without changing stored issuer data or sign-ins.

## Overview

G37 records keyword search across programs, cards, and benefits. The owner selected a top search icon on 2026-11-13, replacing the earlier bottom Search tab idea. Add the icon to Rewards, Benefits, and the opened card page. Each entry opens the same full-screen global search; it does not restrict results to the originating tab. Rewards, Benefits, and Settings remain the three bottom destinations. Search hides the bottom bar while open and uses an accessible Back control.

Reuse Kotlin, Compose, coroutines, Room, the catalog, and existing navigation. Build a small pure matcher and a lifecycle-aware adapter over existing local records. Do not add a server, search dependency, persistent index, Room full-text table, schema migration, analytics, or new credential access. The current CatalogSearch serves Add program and retains its existing behavior. No new application scaffold is needed for this installed app.

## Goals First

**Target problem**: Finding a remembered benefit or card currently requires browsing multiple programs and card categories.
**Persona**: The phone owner looking for an item in their added loyalty programs and stored card benefits.
**Observable outcome**: Enter a partial keyword such as `Delt`, choose a program/card/benefit match, see the correct destination, and return to the same search results or originating list without a refresh or sign-in.
**Grounding**: No STRATEGY.md, constitution, or docs/solutions/ store was found in this checkout. Existing authority is G37, CLAUDE.md, the handbook, the owner's top-icon decision, and the v0.3.1 Benefits redesign. No strategy or constitution is invented for this feature.

## Definition of Done

1. Search is reachable through a visible, labeled top icon on Rewards, Benefits, and card pages. Its touch target is at least 48 dp, its accessible name is `Search`, and no bottom Search tab is added. Existing header actions and centered branding remain usable at narrow width and 200% font size.
2. Search only added programs and their locally stored cards and displayed benefits, including local welcome bonuses created by v0.3.1. Disconnected programs remain searchable when still added; removed programs and cleared card records disappear. Unadded programs remain discoverable through the existing Add program screen. The owner confirmed this corpus on 2026-11-13.
3. Match program display names, program IDs, and category labels; card product names; and displayed benefit titles and descriptions. Queries use case-insensitive token substring matching with Locale.ROOT, collapsed whitespace, and punctuation treated as separators on both query and searchable text. Every query token must match across the entity's own combined fields plus its parent program/card display names, and at least one token must match the entity's own fields. Parent names alone cannot make every descendant match. `Delt` matches Delta; `Delta lounge` matches a lounge benefit when Delta appears in its parent card/program name and lounge appears in the benefit. A parent-only query does not include descendants lacking a matching token of their own. Symbols-only and whitespace-only queries show the start prompt. Card digits, balances, credentials, and hidden raw issuer rows are not searchable fields. Bound input to 256 characters and test that boundary; no fuzzy matching, synonyms, or semantic search. The owner confirmed contextual matching on 2026-11-13.
4. A blank query shows `Search programs, cards, and benefits` with no all-data dump and no recent-search list. Results update as the user types. Group by program alphabetically; within each group show matching program first, matching cards next, then matching benefits grouped by card. Sort cards and benefits alphabetically, with stable IDs as tie-breakers. Show entity labels, program/card context, matching description context when applicable, and an accurate total of actionable results. Group headings are not counted. Identical titles on distinct cards or periods remain distinct.
5. Search uses the same v0.3.1 presentation projection and duplicate resolution as the destination. One combined tracker/list item produces one result; retained descriptions and aliases from either source can match it. It never deletes raw rows, independently guesses duplicate identity, or changes extraction counts. Completed and collapsed-category items remain searchable. Show existing stale-data information when available; never imply that searching refreshed data.
6. Program results open and reveal the matching Rewards tile. Card results open the matching Benefits card page. Benefit results open that card, temporarily expand its category, scroll to the canonical displayed item, and visually identify it with an accessible announcement. Temporary reveal does not rewrite the saved collapse or sort preferences. A removed target gives a clear unavailable message and safe navigation; a removed benefit never falls back to a different benefit with a similar title. Existing occurrence-position benefit keys can be reused after an equal-title/equal-period duplicate disappears. Bind selection to an opaque in-memory source snapshot revision and invalidate the target if that source revision changes before validation/reveal, unless the integrated presentation contract proves a stronger identity. A stableKey membership test alone is insufficient. If conservatively invalidated, show `Results changed. Select the item again` and recompute results; never add a schema migration just to claim an unprovable identity.
7. The keyboard opens on a fresh search entry; Clear empties the query and retains focus. System Back first follows Android keyboard dismissal behavior, then exits the search screen; the visible Back control closes search directly. Returning from a selected item restores the search query and results position. Closing search restores the originating tab/card and scroll state. A fresh entry starts blank. Keep query/result navigation state in memory across configuration changes, but do not persist query text in Room, DataStore, saved-state bundles, logs, analytics, or crash messages; a process restart starts blank.
8. Search observes committed local updates while visible, cancels obsolete matching work, and discards late results. Removed accounts/cards cannot remain actionable through cached results. Reading errors show a generic error with an explicit local retry and never silently masquerade as zero matches. Slow reads show loading; retain an already loaded result set only with a visible updating/unavailable state and target revalidation on selection. No network call, issuer refresh, reconnect, or acknowledgement is initiated by entering a query or selecting a result.
9. Observe the actual APK flow with synthetic data, including narrow/large-font layouts, keyboard, Back, every result type, hidden categories, duplicates, removal, failed reads, and refresh updates. Use an emulator for destructive test installation. Measure final query-to-visible latency on a declared synthetic set of 25 programs, 100 cards, and 2,000 displayed benefits: target p95 <= 200 ms after data is loaded, excluding keyboard animation. Record device, build, sample count (at least 30 settled queries), and measured result. A miss remains blocking until corrected or explicitly accepted with a recorded limit.
10. Required focused and full local gates, privacy checks, handbook verification, owner phone verification, and independent Goal-vs-codebase review pass. One local commit closes each implementation phase; only the final phase may publish implementation work. Green merged integration precedes any release. This planning request creates no application implementation authority.
