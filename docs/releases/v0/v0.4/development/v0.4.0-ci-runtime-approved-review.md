## Runtime Boundary

The workflow retains `pull_request` as its sole trigger. Protected-target validation is scoped at the job level to develop/main, leaving the aggregate job unconditional. It uses the ordinary checkout merge candidate, not an explicitly selected feature head. Full invokes `scripts/validate.py --profile full --platform ci-linux --quiet`; this includes fast checks, JVM tests, lint, debug build, instrumentation compilation, coverage, handbook checks and security. Capture remains excluded remotely under ADR-0001.

Runtime provisioning uses the existing Android SDK tools to install an API 36 Google APIs x86_64 image, create a temporary AVD and launch it headlessly on port 5554. The workflow requires `/dev/kvm`, grants only the hosted runner user access, checks acceleration, records emulator version/acceleration, waits for the exact assigned serial, checks process survival during boot and requires `sys.boot_completed=1`. Setup and job timeouts bound failures. The runtime step explicitly sets `ANDROID_SERIAL=emulator-5554` and invokes the existing `platform` profile. That profile independently verifies `ro.kernel.qemu=1` before `connectedDebugAndroidTest`; its child environment also sets the exact emulator serial. No owner phone is a target.

## Failure Propagation

| Failure | Configured result |
|---|---|
| Full validator or dependency setup fails | Later ordinary setup/runtime steps do not execute; always-run reporting and artifacts remain available where their prerequisites exist. The job remains failed. |
| SDK installation, AVD creation, missing KVM, acceleration or emulator startup fails | The setup step fails or times out. There is no fallback that skips runtime and returns success. |
| Emulator exits or does not finish boot | Process/boot checks fail, preventing platform execution. The exact serial is used throughout. |
| Emulator guard or native tests fail | The platform profile returns nonzero; the enclosing job fails. |
| Aggregate report passes after an earlier step failed | GitHub still retains the earlier job failure; a passing summary cannot turn that job green. The required aggregate demands the job's literal `success`. |
| Report is missing, stale or fails | Always-run aggregation returns its failure after attempting summary publication. It does not rerun validators. |
| Cleanup cannot stop the verified emulator | Cleanup is bounded and cannot create a passing protected-target aggregate from a failed job. It only sends an emulator kill after checking the assigned serial is an emulator. |

The report/profile implementation preserves separate full and platform receipts. The workflow uploads reports on every result with explicit seven-day retention. Actual hosted provisioning availability, image download/boot duration and the unchanged native latency threshold remain execution questions for the first PR run, not proven by these source checks.

## Isolation And Security

The workflow has read-only contents permission, SHA-pinned actions, checkout credentials disabled, no secret input, no privileged pull-request trigger and no owner captures. The existing pinned Docker scanner dependency and repository scanner policy remain unchanged. Fork code runs within the same ordinary hosted validation boundary; this review does not introduce privileged access to owner data. The narrow `/dev/kvm` ACL change is confined to the ephemeral hosted runner.

The [protection receipt](v0.4.0-protection-applied.json) records owner-authorized before/after verification for develop/main: pull requests required with zero approving reviewers, administrator enforcement enabled, and the same `CI result` check bound to app ID 15368. Its recorded 422 correction removed redundant request representation; the returned check identity/binding and other settings were preserved. This review inspected that receipt and did not independently call GitHub or test a forbidden push.

The approved runtime configuration now closes the previous missing-execution-path difference; the protection receipt supplies actual external-setting evidence for its separately approved change. T015 can conclude its local comparison with that explicit boundary; a claim of observed operational CI success must await T020.

At T020, retain the actual PR merge-candidate SHA, selected full/platform/report results, emulator metadata, 68-case-equivalent complete native result and the required `CI result` terminal outcome. If hosted setup, timing or validation fails, the phase reopens under T020: reproduce/classify locally, apply the narrow authorized repair, rerun affected checks and use the existing bounded re-push authority. Merge requires the real required check green and the applicable approval. This review supplies neither publication authority nor that future execution result.
