## Overview

The current Benefits screen renders text-only card tiles, and the card page renders the stored sections in issuer order. There is no card artwork, independent section collapse, user sorting, or alert acknowledgement action. Reading all benefits also exposes listed entries that repeat tracked benefits. The redesign must change the visible experience, not reduce stored benefits to make the screen appear less repetitive.

Use the existing Kotlin/Compose screens, ViewModel, Room repositories, and DataStore patterns. Keep display category, sort, collapse, and duplicate matching separate from the issuer sections used by extraction and section-scoped storage. Prefer a pure presentation transformation over a database migration when no new persisted fact is required. Acknowledgements and user-entered welcome-bonus setup need a deliberate local persistence design, with no remote service or new credential access.

## Definition of Done

1. **Alerts**: Card tiles show the active alert count with a yellow warning badge and accessible text. Opening the card shows its alerts at the top in a distinct format. Each alert has an acknowledgement action; acknowledged alerts disappear and the count updates. Acknowledgement survives navigation and app restart, and a later successful relevant refresh can reintroduce an alert that is still applicable. A failed or cancelled refresh alone does not reset acknowledgement. Alert acknowledgement does not erase enrollment, benefit, or reminder data.
2. **Card images**: All four known Amex card products have matching bundled artwork on their tiles and card pages. Artwork is independent of account identifiers, works offline, and has a generic fallback for an unknown product. No real account capture is used as an image asset.
3. **Organization**: Benefits are organized by program, then card. Card sections appear as Welcome bonus, Credits, Spend trackers, Other. A completed item stays associated with its meaningful category and has clear completed styling. Existing descriptions, progress, period information, enrollment status, and freshness information remain available.
4. **Sorting**: Items are alphabetical within each category by default, with an explicit completed-items-last option. Sorting is stable for equal titles, does not reorder stored issuer data, and retains the user's choice across navigation and app restart.
5. **Collapsing**: Each category can expand or collapse independently, with a visible count and accessible expanded/collapsed state. Other, the least important category, starts collapsed; actionable categories start expanded. User choices survive navigation and app restart and are scoped so changing one card does not change another card's sections. Collapsing a category does not hide the top-level alerts.
6. **Redundancy**: A listed entry that represents a tracker on the same card appears once in the normal display. The retained display includes useful description and enrollment information from either source. Distinct periods and different benefits with similar names are not combined. Raw stored rows and the extraction count evidence are preserved; duplicate suppression changes presentation only.
7. **Related Benefits requests**: Preserve the previously requested benefit/alert counts, a generic empty message, and navigation from a Rewards program with benefits to that program in Benefits (G36). Include a visible per-list freshness note when a list refresh fails while trackers refresh (G43), based on reliable section-read outcome rather than a whole-card timestamp alone. Include the previously requested local manual welcome-bonus setup without restoring manual account balances or exposing credentials.
8. **Actual behavior**: A runnable synthetic-data screen exercises every requirement, including restart persistence, unknown artwork, failed refresh, duplicate ambiguity, completed items, and multiple cards. Observe narrow and large-font layouts, TalkBack labels, taps, navigation, sorting, collapse, acknowledgement, and alert return after a successful refresh. Install the tested APK with `adb install -r` and obtain owner verification of the real redesigned phone screens before declaring delivery complete. Synthetic screenshots alone do not establish phone delivery.
9. **Regression and publication**: Required local tests and checks pass; the Amex benefits reader retains its section-scoped writes, full stored count minima, enrollment data, and 120 s budget. Existing owner site-count confirmation remains explicit. Publish through a version-authorized integration PR only after the required local/manual gates; merge only on green CI result, release through the release workflow, and close/archive v0.3 only when both plans and the remaining original completion duties are satisfied.
