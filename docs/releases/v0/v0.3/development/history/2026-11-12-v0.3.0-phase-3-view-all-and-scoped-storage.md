## Sub-tasks

- **T012.** ADR-0008 amendment: option (B), the page script presses the page's own view-all link (option A, the bare address, rejected as untested; option C kept for a card without the link); a per-card state table (awaitingRewards, awaitingViewAll, complete or listUnread); section-scoped storage described.
- **T013.** `BenefitsRead` carries per-card `sections` (a card missing from the map covered every section; tracker sections are spend progress, credits, completed, and other; the list section is listed). `CardRepository.applyCardBenefits` takes `sections` (default: all, so every existing caller keeps the full replace); `RoomCardRepository` deletes and inserts only those sections in one transaction (`CardDao.deleteBenefitSections`); an empty set changes nothing and stamps nothing. `SyncManager.applyBenefits` passes each card's sections. The test fake merges by section.
- **T014.** `extract.js`: a ready Rewards page with no activity link but a view-all link (and a second page allowed) posts its trackers with `next=viewAll`, then presses the view-all link with a handoff note; a view-all page posts its list with `page=viewAll`. `BridgeProtocol` accepts `viewAll` pages and `next` only as `viewAll` on a Rewards message with no list; the Amex spec accepts `/card-benefits/view-all`. The per-card state lives in the new pure `BenefitsCardReads`; `HeadlessWebViewBenefitsSource` routes messages through it, treats an unreadable page in the view-all step as list unread, and runs a watchdog (page timeout plus 5 s) for a view-all page that never reports. Card lines gain the outcomes `listUnread`; a full list logs a cap hit; the run summary counts dropped messages.
- **T015.** Synthetic `benefits-view-all.html` (card digits from its `card` query value, 4 entries with Enrolled, Enrollment Required, and no mark, a 9-digit decoy membership number) in both fixture folders, and `card=` values on the Hotel and Basic view-all links. Tests listed below.
- **T016.** Tests, secret scan, and CI impact below.

## Plan delta

**Disposition: Incomplete (non-blocking).**

Evidence: the plan's 3.4 placed the late-Rewards-message and other-card view-all cases in `HeadlessSyncFixtureTest`. A real page cannot stage those messages on demand, so the per-card state moved into the pure `BenefitsCardReads` and those cases are JVM tests of it; the on-device test covers the two-page read and the failing view-all page end to end. The ADR's watchdog grace became 5 s (not 2 s) because it starts at the Rewards message, before the view-all page's own cap starts.

Consequence for the remaining phases: Phase 4's live check expects Hilton and Delta to show `kind=viewAll` page lines and stored lists of at least 20 and 24 benefits; G27 can move to Fixed only with that evidence.
