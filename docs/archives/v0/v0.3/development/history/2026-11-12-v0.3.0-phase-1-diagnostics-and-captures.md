## Plan delta

**Disposition: False assumption (non-blocking).**

Evidence: the live diagnostics lines in the capture record. The plan's cause 2 assumed Platinum posts from its Rewards page before the activity link renders. The link was found and followed every time; the read instead posts Rewards content under the activity address, because Amex changes the address without a new document, the page script restarts on that change, and the old content stays on screen for several seconds (`kind=activity trackers=2 activity=true`, which no real activity page shows). The plan's cause 3 mechanism is confirmed in a stronger form: the switch also restarts the script, so the switched state is lost (`switched=false` on switched cards). Causes 1 and the storage defect are confirmed as planned.

Consequence for the remaining phases: Phase 2's ready rules (T006 to T008) must make an activity page ready only once its activity link is gone and its list is steady, and must carry the switched state across the script restart (the app already sends the target card on every page; it can also mark the first page after a switch). Both fit inside T006 to T008's files (`extract.js`, `HeadlessWebViewBenefitsSource.kt`, `BridgeProtocol.kt`, ADR-0008); no plan edit is needed. Phase 3 proceeds (GO). Phase 4's expected counts come from the capture record once the owner confirms them.

A smaller observation: a Rewards page that only follows its activity link posts nothing, so it has no page line of its own (the card line's `pages` count still includes it). Phase 2's rewrite of that step can give it a line.
