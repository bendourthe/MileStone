Repository Overview

MileStone is a native Android app (com.bendourthe.milestone) that shows the points, miles, and rewards cash of the user's loyalty programs on one dashboard, and, for American Express, each card's benefits on a Benefits tab. It reads each balance from the program's own website inside an embedded browser (Android WebView) after the user signs in once, and keeps those sign-ins alive in the background. Nothing is entered by hand, and no server is involved: every balance, sign-in, and saved password stays on the phone.

The remote origin is https://github.com/bendourthe/MileStone.git. main is the release branch and develop is the integration branch. The version is the latest heading in the root CHANGELOG.md.

Toolchain

  • Kotlin, Jetpack Compose (Material 3), Gradle with a version catalog (gradle/libs.versions.toml).
  • compileSdk 37, targetSdk 36, minSdk 29.
  • Build types: debug, release, and capture. capture is a debug copy with the suffix .capture and the label "MileStone Capture"; it adds a "Capture page" action that saves a page for selector work. Captures are copied to the PC through app/src/capture/sanitize_capture.py, which strips identifiers on the way, and inspected only through inspect_capture.py, which prints structure with text masked. CI never builds it (ADR-0001).
  • The debug build adds a "Site check" launcher entry (app/src/debug) for testing whether a program's site works in the embedded browser.

Local gate, run from the repository root in PowerShell:

.\gradlew.bat -q testDebugUnitTest lintDebug assembleDebug assembleCapture compileDebugAndroidTestKotlin

CI (.github/workflows/ci.yml) runs ./gradlew testDebugUnitTest lintDebug assembleDebug compileDebugAndroidTestKotlin on Ubuntu with Java 17.

Module Layout

All code is in the single app module under com.bendourthe.milestone.

PackageResponsibility
domainModels (Program, ExtractionSpec, BenefitsSpec, SyncResult, FailureReason, BalanceUnit), card and benefit models with stable keys (Benefits.kt: a card is its program plus last digits; a benefit is its card plus title or the issuer's list key plus period), BenefitPeriods (period labels to end dates), repository interfaces, catalog search, and the dashboard use case. No Android types.
data.catalogStaticCatalogRepository: the 14 programs, their hosts, sign-in and balance URLs, and fixture-verified XPath or CSS balance selectors, and for American Express the benefits pages and selectors (AMEX_BENEFITS, ADR-0008). Hosts come only from the feasibility record.
data.dbRoom database version 3 (loyalty_accounts, balance_snapshots, cards, benefits, benefit_reminders; cards, benefits, and reminder records cascade from their account or card), RoomCardRepository, schema exports in app/schemas/.
data.sessionTinkSessionStore: encrypted per-program session metadata (connected and verified times), never cookies.
data.credentialsCredentialVault: saved sign-ins sealed with AES-256-GCM under an Android Keystore key (StrongBox when available), one file per program in noBackupFilesDir/signins (ADR-0004).
data.settingsDataStore preferences (sort mode).
syncSyncManager, the single writer of balances and statuses, with per-program throttle, backoff, and refresh reasons (ON_START, MANUAL, KEEP_ALIVE); ForegroundSyncObserver refreshes when the app opens.
sync.webviewThe login bridge: WebViewConfig (hardened settings and a full-height layout, without which Chromium lays pages out with a zero viewport height and every vh length is 0), HostPolicy (exact-host allow list), SessionProfiles (one WebView profile and cookie store per program), BridgeSession (the page-state machine), LoginBridge (WebView glue), HeadlessWebViewBalanceSource (refresh without UI), HeadlessWebViewBenefitsSource (the benefits read, card by card), and AutoSignInSupport.
sync.extractBridgeProtocol (messages to and from the page script, with benefits messages accepted only from the catalog's benefits pages), BenefitsReader (field checks, caps, and section rules), BenefitAmountParser, PageStateClassifier, and BalanceParser.
sync.mfaOneTimeCodeInbox and SmsCodeReceiver: texted sign-in codes held in memory for five minutes, matched by sender keywords, handed out once.
sync.backgroundKeepAliveScheduler, KeepAliveReceiver, and KeepAliveService (a refresh every 15 minutes as a short dataSync foreground task), ScheduledRefreshScheduler (an alarm at the next scheduled midnight, allowed while the phone idles), VirtualDisplayWebViewHost (an off-screen WebView), BenefitReminders (the daily credit reminder check, its private notifications, and its 9:00 alarm), and the notification channels.

AppContainer wires these together by hand; there is no dependency-injection framework.

Runtime Flow

  1. The user adds a program from the catalog and signs in inside AuthWebViewModal. The page script app/src/main/assets/extract.js runs only on the program's exact hosts, reads the balance element named by the catalog selector, and posts it back; SyncManager stores it.
  2. SyncManager refreshes programs in a hidden WebView that reuses the program's own cookie store. The user's schedule in Settings (every day, every Sunday by default, or the last day of the month, each at midnight) sets an alarm that refreshes every balance older than that time and may sign in. Opening the app refreshes a program only when it was neither updated nor tried since that scheduled time; a failed program waits for the next scheduled time or the user's Refresh. Every 15 minutes in the background, the keep-alive reads connected programs to keep their sessions alive. Reads share two fetch slots and sign-ins run one at a time; a sign-in the user just started skips that queue.
  3. When a session has ended and the user saved an automatic sign-in, the hidden browser opens the program's sign-in page directly (and skips the session read when the last one already found the session ended), and the page script fills the saved username and password, ticks "remember this device", prefers a texted code, and enters a code that arrives by text. A site that asks for the username alone first gets the username, then at most one more fill on its password page. The script submits with the form's Sign in or Continue button and never presses a show-password toggle. Passwords are typed when the user opens MileStone or at the scheduled refresh, never by the 15-minute keep-alive (ADR-0005). A sign-in counts as refused only when the site shows an error with its form; a form back without an error is unfinished and may be tried again. A refused password is never retried: automatic sign-in pauses for that program until the user taps Sign in or Refresh on its tile, which tries the saved sign-in once more and opens the site for the user if it stops again, or until a sign-in succeeds. A background refresh that needs the user posts a "needs you" notification.
  4. Signing out or removing a program cancels its running refresh or sign-in, erases its WebView profile's cookies and storage at once, and deletes its saved sign-in; a profile still held by a live WebView is deleted at the next app start.
  5. After a saved American Express balance (not for the keep-alive), a separate benefits read opens the Amex Rewards page in the same profile. The page script reports the card switcher's cards (names and last digits only), then presses the switcher option for each next card and follows the page's own activity link for cards that have one. Cards without an activity page post their Rewards trackers before opening their own view-all link for the full list. Each page waits for its own content markers, scrolling to load lower sections and checking that counts and height have settled; after a switch, the new card's trackers must replace the previous card's. At the 15 s Rewards readiness cap, an available activity link is followed even while the page is still growing; a missing lower section can wait up to the app's page timeout, at most 20 s. One deadline bounds the whole benefits read to 120 s, cutting second pages before leaving cards unread when time is short. The read never signs in and never reads an account key (ADR-0008). SyncManager replaces only the sections actually read: a failed view-all page keeps the previous list, and an unread card keeps its previous benefits. A card is removed only when a complete card list no longer shows it. Count-only diagnostics identify page kind, readiness, wait time, card index, and total read time. The Benefits tab shows one tile per card with its next open credit and freshness; a card page groups spend progress, credits, completed items, other items, and the full benefits list with enrollment status.
  6. Once a day at 9:00 and when the app opens, the reminder check posts one private notification per statement credit and period when part of the credit is unused and its period ends within 7 days (monthly), 14 (quarterly), or 30 (half-year and yearly), never from benefits read more than 8 days ago and never twice for the same credit and period. Settings has a Benefit reminders switch, on by default.
  7. Add program opens on programs not added yet, with a filter for Added and All programs; added programs carry a green outline. Programs whose sites do not work in the embedded browser cannot be added, and tapping one says so. Pulling the dashboard down asks "Refresh all programs?" before refreshing everything, since a full refresh can take minutes; the top refresh button refreshes at once. An added program's menu offers Refresh, Sign out, and Remove; "Open in app or browser" was removed (ADR-0002, ADR-0003, ADR-0007).

Privacy Rules

  • Logs name programs and hosts only, never full URLs, page text, balances, cookies, passwords, or codes. DiagnosticLog also appends these lines to no_backup/diagnostics.log (capped at 512 KB), so a stop can be diagnosed after the phone's log buffer rotates; on a debug build, read it with adb shell run-as com.bendourthe.milestone cat no_backup/diagnostics.log.
  • A card is identified on the phone by its last digits only. Full card numbers, account keys, and membership numbers are never stored, logged, or sent; the page script strips grouped digit runs, identifier-like tokens, and account-key-shaped runs before posting, and benefit reminders show only "A card benefit expires soon" on the lock screen.
  • Real captured pages live only in the gitignored app/src/test/resources/fixtures-private/; committed fixtures in app/src/test/resources/fixtures/ are hand-written with fake balances.
  • Cloud backup and device transfer exclude every app data domain (res/xml/backup_rules.xml, res/xml/data_extraction_rules.xml), and the vault sits in noBackupFilesDir, which Android never backs up.

Tests

  • Unit tests (app/src/test, Robolectric where Android types are needed) cover the catalog, Room and its migrations, cards and benefits storage, the vault, the code inbox, the bridge state machine and benefits protocol, SyncManager with its benefits read, period labels and reminders, the Benefits screens, and ExtractorFixtureTest and BenefitsFixtureTest, which run every selector against its synthetic fixture and, locally, its private capture.
  • Instrumented tests (app/src/androidTest) cover WebView configuration, headless sync and the benefits read against local fixtures (with identifier decoys), a reminder notification, and screenshots of the Benefits screens. Running them uninstalls the app, which clears every sign-in and saved password.

The Amex benefits reader companion describes page readiness, card switching, time limits, and section-scoped storage in more detail. Both sources are included in the offline handbook.

Amex Benefits Reader

The benefits read starts after a saved American Express balance, in the same program profile. It reads cards and benefit sections from the site's existing controls. It never signs in, composes an account-key URL, or fetches account data from another service.

Page Kinds

PageRoleSuccessful result
RewardsLists the cards and starts a card readFollows the card's activity link, or posts trackers before following its view-all link
ActivityHolds the full tracker set and list for cards that offer itStores every covered section for that card
View-allHolds the full list for cards without an activity pageJoins the list to the Rewards trackers

Navigation presses the page's own link or card-switcher option. The app accepts benefits messages only on the configured Amex host and page paths, with the expected message nonce and page kind.

Readiness

The script scrolls to load lower sections. A shape is steady when tracker count, listed-link count, and page height stay unchanged for two seconds. A page with no trackers gets a longer empty settle.

  • Rewards requires an activity or view-all link, a reached bottom, and settled content. At its 15-second readiness cap, an available activity link is still followed. A missing lower section may wait up to the supplied page timeout, capped at 20 seconds.
  • Activity requires its own content: the Rewards activity link must be absent, and at least one tracker or listed link must exist. Rewards content under an activity address is never accepted as an activity read.
  • View-all requires listed content whose count differs from the page it was opened from, then bottom and settle checks. A capped empty list does not erase the previous list.

Before pressing a link, the script leaves a document-local handoff note. An in-place address change adopts that note; a full document load drops it. After pressing an activity link, the script waits for navigation or a bounded unreadable result instead of posting partial Rewards trackers.

Card Switching

The selected card must match the target, and its tracker fingerprint must be nonempty and different from the previous card's. The fingerprint stays inside the script and is never posted. An emptied tracker area is not proof that the new card has loaded.

The switch cap is 12 seconds. A settled empty tracker area with the right markers may become an empty read after that cap. Old trackers still on screen produce a mismatch, preserving the stored card rather than assigning another card's trackers to it.

Run Budget

One deadline covers the whole 120-second benefits read, with margins for script and app cleanup. Each page gets at most 20 seconds and cannot extend the shared deadline.

At a card's first page, the scheduler reserves 20 seconds for its possible second page and 20 seconds for every remaining first page, including the current one. If that time is unavailable, it cuts second pages for this and all later cards. If fewer than 10 seconds remain for another card to start, it leaves that card unread. These cuts preserve stored sections that were not reached.

The 20-second first-page reserve includes a late Rewards lower section. Reserving only 15 seconds could spend time on an earlier activity page and leave the last card unread.

Storing a Read

BenefitsCardReads records which sections a card's pages covered. Rewards alone covers tracker sections. A successful view-all adds the listed section. An activity page covers every section. A failed or mismatched view-all keeps the new trackers and the previous stored list.

SyncManager sends those section sets to RoomCardRepository. The repository deletes and replaces only those sections in a transaction under the program lock. A failed card keeps its previous benefits. Cards disappear only when a complete card list no longer contains them.

Diagnostics

Benefits diagnostics hold fixed page kinds, bounded counts, readiness reasons, wait times, card indexes, and the run total. They do not hold benefit text, amounts, card digits, account keys, page queries, or sign-in values. Card outcomes distinguish read, unread-list, and mismatch results; a read outcome alone does not prove that every benefit was loaded.

Card freshness alone does not prove that its list was refreshed: trackers can be new while a failed list keeps its older contents. The visible per-list freshness note is tracked separately from the extraction fix.

Verification

Synthetic WebView fixtures exercise late lower sections, in-place address changes, card switching, view-all navigation, and failed-list preservation. JVM tests cover the protocol, budget, card-read transitions, and real Room section replacement. Private-capture tests run locally, and their contents are never committed or printed.

Instrumented tests run on the emulator only. Running them on the owner's phone uninstalls the app and clears sign-ins. Live phone verification uses adb install -r, keeps the app in the foreground, and records only per-card section counts, enrollment counts, diagnostics, and read times. The database copy used for counts is deleted immediately afterward.

Limits

The site can change or load too slowly for the budget. The read preserves sections explicitly left unread, while a capped page can contain only the content loaded before its cap. Card freshness alone is not proof of completeness. Background continuation, automatic retry policy, benefit sorting and grouping, and alert presentation belong to separate work. The architecture decision is ADR-0008.

Privacy

Only named fields are read, and diagnostics remain count-only.

  • Exact host and path checks, a nonce, and message-field checks guard the bridge.
  • Account keys, full card numbers, cookies, and sign-in data stay out of diagnostics.
  • Private captures stay local; notifications use private lock-screen text.

Privacy Rules

  • Logs name programs and hosts only, never full URLs, page text, balances, cookies, passwords, or codes. DiagnosticLog also appends these lines to no_backup/diagnostics.log (capped at 512 KB), so a stop can be diagnosed after the phone's log buffer rotates; on a debug build, read it with adb shell run-as com.bendourthe.milestone cat no_backup/diagnostics.log.
  • A card is identified on the phone by its last digits only. Full card numbers, account keys, and membership numbers are never stored, logged, or sent; the page script strips grouped digit runs, identifier-like tokens, and account-key-shaped runs before posting, and benefit reminders show only "A card benefit expires soon" on the lock screen.
  • Real captured pages live only in the gitignored app/src/test/resources/fixtures-private/; committed fixtures in app/src/test/resources/fixtures/ are hand-written with fake balances.
  • Cloud backup and device transfer exclude every app data domain (res/xml/backup_rules.xml, res/xml/data_extraction_rules.xml), and the vault sits in noBackupFilesDir, which Android never backs up.

Diagnostics

Benefits diagnostics hold fixed page kinds, bounded counts, readiness reasons, wait times, card indexes, and the run total. They do not hold benefit text, amounts, card digits, account keys, page queries, or sign-in values. Card outcomes distinguish read, unread-list, and mismatch results; a read outcome alone does not prove that every benefit was loaded.

Card freshness alone does not prove that its list was refreshed: trackers can be new while a failed list keeps its older contents. The visible per-list freshness note is tracked separately from the extraction fix.

The database copy used for counts is deleted immediately afterward.

Limits

The site can change or load too slowly for the budget. The read preserves sections explicitly left unread, while a capped page can contain only the content loaded before its cap. Card freshness alone is not proof of completeness. Background continuation, automatic retry policy, benefit sorting and grouping, and alert presentation belong to separate work. The architecture decision is ADR-0008.
