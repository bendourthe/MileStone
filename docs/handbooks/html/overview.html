Repository Overview

MileStone is a native Android app (com.bendourthe.milestone) that shows the points, miles, and rewards cash of the user's loyalty programs on one dashboard, and, for American Express and Chase, each card's benefits on a Benefits tab. It reads each balance from the program's own website inside an embedded browser (Android WebView) after the user signs in once, and keeps those sign-ins alive in the background. Account balances are read automatically; optional welcome-bonus spending is entered locally. No server is involved: every balance, sign-in, and saved password stays on the phone.

The remote origin is https://github.com/bendourthe/MileStone.git. main is the release branch and develop is the integration branch. The version is the latest heading in the root CHANGELOG.md.

Toolchain

  • Kotlin, Jetpack Compose (Material 3), Gradle with a version catalog (gradle/libs.versions.toml).
  • compileSdk 37, targetSdk 36, minSdk 29.
  • Build types: debug, release, and capture. capture is a debug copy with the suffix .capture and the label "MileStone Capture"; it adds a "Capture page" action that saves a page for selector work. Captures are copied to the PC through app/src/capture/sanitize_capture.py, which strips identifiers on the way, and inspected only through inspect_capture.py, which prints structure with text masked. CI never builds it (ADR-0001).
  • The debug build adds a "Site check" launcher entry (app/src/debug) for testing whether a program's site works in the embedded browser.

The canonical validation entrypoint is scripts/validate.py. The fast profile checks the private-input boundary, Python and extractor syntax, and handbook freshness. The full profile adds validation-helper tests, unit tests, lint, debug and local capture builds, instrumented-test compilation, coverage, Room schema checks, handbook browser checks, and secret scanning. Full validation needs the Playwright dependency in scripts/requirements-validation.txt and its Chromium browser, plus installed Gitleaks or the documented preloaded Docker image; the profile does not install those tools.

Local full gate, run from the repository root in PowerShell:

python scripts/validate.py --profile full --quiet

Use python scripts/validate.py --profile fast --quiet for the smaller checks. --list --json lists a profile's commands without running them or writing reports. Profiles write results under reports/ by default; python scripts/validate.py --profile report --quiet aggregates existing receipts without rerunning checks. The collector preserves JUnit exports and rejects reported failures or errors even if Gradle returns zero; the platform profile requires JUnit cases from both its debug functional task and its optimized Search task, rejects skipped runtime cases, and ignores unrelated variant reports. The release profile packages a clean committed source archive, verifies reproducible archive bytes and safe paths, and records version, commit, and SHA-256 metadata. It does not build an APK, use signing secrets, rerun tests, publish, or tag a release; debug sideloads remain separate.

The local emulator runtime gate is separate from full:

python scripts/validate.py --profile platform --quiet

This profile accepts only emulator-5554, verifies ro.kernel.qemu is 1, and sets each test child's ANDROID_SERIAL to that emulator. It runs the debug functional suite with only the optional debug latency diagnostic excluded, then measures the shared Search scenario through searchBenchmark against a non-debuggable, R8-optimized benchmark app. The 30 samples, three warmups, real visible-draw endpoint, animated background and 200 ms p95 limit remain unchanged. Both tasks and their JUnit evidence must pass. Benchmark artifact metadata also binds the measured run to its parent validation invocation. A failed native runtime step can trigger one separate scheduler/frame diagnostic only when current invocation, source, APK and completed latency-failure evidence match. Missing or malformed evidence skips collection. Diagnostic output never qualifies the original failed gate; native cleanup failures or an unfinished trace worker keep the diagnostic failed and report cleanup uncertainty. The native profile retains fresh UUID-correlated metrics in reports/metadata/search-latency.json and expected APK hashes in search-benchmark-artifacts.json; the controller checks the installed target and controller hashes before measuring. Do not run connected tests against the owner's phone: installing the test app clears its sign-ins. Instrumented-test compilation in full is not runtime proof.

CI (.github/workflows/ci.yml) is configured to validate pull requests to develop or main on Ubuntu 24.04 with Java 17. After preparing the pinned dependencies, it runs .validation-venv/bin/python scripts/validate.py --profile full --platform ci-linux --quiet, installs the Android 36 Google APIs x86_64 image, verifies KVM acceleration, boots an isolated headless emulator-5554, and runs .validation-venv/bin/python scripts/validate.py --profile platform --platform ci-linux --quiet. Emulator cleanup, report aggregation, and report upload are configured to run even after failure. CI result requires the validation job to succeed for those target branches. The explicit ci-linux full profile still excludes the local-only capture build under ADR-0001.

Module Layout

Production code is in the app module under com.bendourthe.milestone. The test-only searchBenchmark module runs its own instrumentation process so normal release shrinking does not remove APIs that its runner expects. app/src/searchScenario/ holds one synthetic scenario shared by the debug diagnostic and optimized fixture. app/src/benchmark/ supplies a signature-protected, emulator-only activity in a separate .benchmark package, with an empty Application and disabled production entry points. These fixtures are absent from the normal debug, capture and release app APKs; they use an in-memory database and private scratch preferences rather than issuer sessions.

Its dark teal gradient and three drifting glows share a minute-long loop and stay still when system animations are off.

The aurora rasterizes its base gradient and three glows into a high-precision image owned by each background, with a longest side of at most 256 pixels, then scales that opaque image across the background in one draw. It reuses the image while the phase stays unchanged, updates it at the current continuous phase, and replaces it when its raster dimensions change. The original glow positions, radii and minute-long motion remain unchanged. The native rendering regression compares the output with the original separate-gradient reference across phases, viewports including 1080x2340, and color buffer formats; this color comparison does not qualify Search timing.

AppContainer wires these together by hand; there is no dependency-injection framework.

Runtime Flow

  1. The user adds a program from the catalog and signs in inside AuthWebViewModal. The page script app/src/main/assets/extract.js runs only on the program's exact hosts, reads the balance element named by the catalog selector, and posts it back; SyncManager stores it.
  2. SyncManager refreshes programs in a hidden WebView that reuses the program's own cookie store. The user's schedule in Settings (every day, every Sunday by default, or the last day of the month, each at midnight) sets an alarm that refreshes every balance older than that time and may sign in. Opening the app refreshes a program only when it was neither updated nor tried since that scheduled time; a failed program waits for the next scheduled time or the user's Refresh. Every 15 minutes in the background, the keep-alive reads connected programs to keep their sessions alive. Reads share two fetch slots and sign-ins run one at a time; a sign-in the user just started skips that queue.
  3. When a session has ended and the user saved an automatic sign-in, the hidden browser opens the program's sign-in page directly (and skips the session read when the last one already found the session ended), and the page script fills the saved username and password, ticks "remember this device", prefers a texted code, and enters a code that arrives by text. A site that asks for the username alone first gets the username, then at most one more fill on its password page. The script submits with the form's Sign in or Continue button and never presses a show-password toggle. A successful password submission starts the existing page window again so a delayed saved-password fill still allows the existing second press; retry counts and the overall 180-second sign-in limit are unchanged. Passwords are typed when the user opens MileStone or at the scheduled refresh, never by the 15-minute keep-alive (ADR-0005). A sign-in counts as refused only when the site shows an error with its form; a form back without an error is unfinished and may be tried again. A refused password is never retried: automatic sign-in pauses for that program until the user taps Sign in or Refresh on its tile, which tries the saved sign-in once more and opens the site for the user if it stops again, or until a sign-in succeeds. A background refresh that needs the user posts a "needs you" notification.
  4. Signing out or removing a program cancels its running refresh or sign-in, erases its WebView profile's cookies and storage at once, and deletes its saved sign-in; removing a program also signs out each of its additional sign-ins; a profile still held by a live WebView is deleted at the next app start.
  5. After a saved American Express balance (not for the keep-alive), a separate benefits read opens the Amex Rewards page in the same profile. The page script reports the card switcher's cards (names and last digits only), then presses the switcher option for each next card and follows the page's own activity link for cards that have one. Cards without an activity page post their Rewards trackers before opening their own view-all link for the full list. Each page waits for its own content markers, scrolling to load lower sections and checking that counts and height have settled; after a switch, the new card's trackers must replace the previous card's. At the 15 s Rewards readiness cap, an available activity link is followed even while the page is still growing, and so is a view-all link when trackers are on screen; a missing lower section can wait up to the app's page timeout, at most 20 s. One deadline bounds the whole benefits read to 120 s, cutting second pages before leaving cards unread when time is short. The read never signs in and never reads an account key (ADR-0008). SyncManager replaces only the sections actually read: a failed view-all page keeps the previous list, and an unread card keeps its previous benefits. A card is removed only when a complete card list no longer shows it. Count-only diagnostics identify page kind, readiness, wait time, card index, and total read time. The Benefits tab groups cards by program with matching offline artwork, benefit counts, yellow alert counts, next open credit, and freshness. The card display and acknowledgement rules are described below.
  6. After a saved Chase balance, the Chase benefits read visits each Chase sign-in in its own profile within the same 120 s budget (ADR-0009). The page script follows the owner's path (a card on the dashboard, More, Benefits), lists the cards in the Benefits card selector, and reads each card's benefit groups, rows, and welcome tracker, pressing the selector for the next card. It stops without choosing anything on an identity check, never presses a payment control, and never signs in. A card already read through an earlier sign-in is skipped. A card's identity is an HMAC-SHA256 of its selector option under a key kept in noBackupFilesDir, so the raw option id is never stored; the stored card gets an opaque local id. SyncManager applies each sign-in's card list (only a complete list can remove a card, and only from that sign-in's coverage; a complete list that shares no card with the sign-in's coverage changes nothing) and the benefits read per card. A card whose page has more rows, groups, or trackers than the read may post is left unread rather than stored partially. A card read stopped by the deadline or a page limit keeps its stored benefits, and the read is reported as stopped. The page limit grows with the number of listed cards, so a site that reloads the page per card still finishes. A path that stalls before the card list starts over once from the dashboard. Leaving MileStone cancels a running benefits read (Amex or Chase); the next time MileStone returns to the screen, that read starts again even when no balance is due.
  7. Once a day at 9:00 and when the app opens, the reminder check posts one private notification per statement credit and period when part of the credit is unused and its period ends within 7 days (monthly), 14 (quarterly), or 30 (half-year and yearly), never from benefits read more than 8 days ago and never twice for the same credit and period. Settings has a Benefit reminders switch, on by default.
  8. Add program opens on programs not added yet, with a filter for Added and All programs; added programs carry a green outline. Programs whose sites do not work in the embedded browser cannot be added, and tapping one says so. Pulling the dashboard down asks "Refresh all programs?" before refreshing everything, since a full refresh can take minutes; the top refresh button refreshes at once. An added program's menu offers Refresh, Sign out, and Remove; "Open in app or browser" was removed (ADR-0002, ADR-0003, ADR-0007).

Benefits Display

The bottom tabs always open their own first page: Rewards returns to the Rewards page from a card page, and Benefits opens on its program page. Below a tab's first page, a horizontal swipe to the right goes back one page and follows the finger, and a swipe to the left reopens the page last left; a page fades out drifting in the swipe's direction before the next fades in, so two pages never show together.

Benefits starts with one tile per tracked institution that supports card benefits, with its card count and a small alert badge at the top right. Pressing an institution opens only its cards; card Back returns to that card list and list Back returns to the institutions. Connected institutions remain visible before their cards are read. Tapping a supported program on Rewards opens its card list directly; reminders open the named card with the same parent hierarchy. Each institution's page lists Personal cards, then Business cards, under collapsible headers styled like the Rewards category headers, which also collapse. A compact card tile shows the artwork, the name with its alert badge, the ending and benefit count, and the completed count with the last update. Products on the bundled public product list (CardProducts, 69 Chase and Amex products) show their offline artwork and their product name, shortened to the product ("The Platinum Card from American Express" shows as "Platinum"; Chase's "CHASE SAPPHIRE" is the Sapphire Preferred); another card shows the issuer's name without the issuer's own words or a trailing "Card", recased when written in capitals. Artwork is clipped in proportion to its size, so no image corner shows; an unknown product shows a drawn card in the issuer's color with its ending. Each card page shows the card, then its alerts as slim rows with Acknowledge on the right (swiping a row right also acknowledges it), then groups Welcome bonus, Credits, Spend trackers, and Other. The top-right sort menu offers Name A-Z (the default), Name Z-A, Deadline soonest, and Largest amount remaining within each category, with unknown dates or amounts last. The separate top-right filter menu holds Completed last, applied before the selected sort. Both choices are saved per card. Outlined, counted category headings have explicit Show/Hide controls and collapse independently, with Other initially collapsed. Completed items retain their category with a check and strike-through; an unknown completed kind remains in Other rather than being inferred from its amount. Completed credits show a full progress bar. The display uses a positive stored target, then a single explicit leading dollar amount in the completed credit title, to show the completed target/target ratio beside the bar. An earned amount alone never establishes a target; when no target is known, the actual earned label remains beside the full bar. Unknown or multiple dollar amounts are not inferred. This display-only fallback does not change stored issuer rows. Unfinished credits retain actual progress and the inline ratio; other trackers keep their existing amount labels. Enrolled appears beside the title before the completed check, while Enrollment required remains in the body.

Chase appears as one institution tile. A section shows once a card belongs to it. A card's section is, first match wins: the card page's top-right Show under choice (which survives refreshes), a product name that says Business ("Ink ...", "... Business ..."), the product list's kind, how the Chase home page groups the card (under "Personal" or under a business name; only the ending and a yes/no flag leave the page), and finally Personal when any Personal sign-in reaches the card (ADR-0009). A Chase card with no section yet is listed under Personal with "Needs Personal or Business". A top-bar button opens the Chase sign-ins sheet: each sign-in is listed as Personal or Business with its status, Add personal or Add business adds an isolated sign-in of that kind (up to four, refused with an explanation when the phone cannot keep separate profiles), and an extra sign-in can be signed out, which removes only the cards that no other sign-in reaches. The first sign-in owns the Chase Rewards balance; extra sign-ins never write a balance. Card tiles, Search results, and reminders show the stored card ending and open the exact card by its local id, so two cards with the same ending stay distinct.

The local welcome-bonus form groups amount digits with commas while preserving exact cents and cursor positions. Saved whole-dollar values reopen without .00; fractional cents remain precise. Standalone numbers in the Reward field and local reward description also group with commas, while raw free text, codes and dates remain unchanged. The optional deadline displays YYYY-MM-DD separators during entry and accepts a calendar selection. Choosing a calendar date changes the draft only; Save commits the setup. Calendar dates are converted in UTC so the selected calendar day stays unchanged across time zones. Invalid amounts or dates show field-specific errors.

A listed entry merges into a tracker only when the same-card title/period match is unambiguous and enrollment statuses do not conflict. Description and enrollment details remain visible on the copied tracker. Raw issuer rows stay stored for refresh, reminders, and count verification. Different periods or ambiguous matches remain separate.

Yellow alerts appear below the card artwork and above the categories, one slim row each with Acknowledge on the right; swiping a row right also acknowledges it. They identify enrollment requirements, unused credits near their established reminder deadline, stale reads, and a listed-benefits section that failed to refresh. Acknowledge hides one alert and updates its count without changing enrollment, issuer rows, or notification records. Acknowledgements survive navigation and restart. Only a successful relevant section read can reintroduce a still-applicable source alert; tracker period changes do not change a retained listed enrollment's identity. Failed or cancelled reads cannot reset it. Local welcome-bonus deadline alerts instead follow the saved manual setup.

Each successful section replacement increments the card's Room read generation in the same transaction. The following DataStore outcome binds to that generation and read time and advances only the sections actually covered. A mismatch or unavailable outcome is labeled unknown; an older list is explicitly identified when only trackers refreshed. A whole-card timestamp alone never proves list freshness. The additive version 3 to 4 migration preserves accounts, benefits, enrollment, and reminder records; the version 4 to 5 migration adds sign-ins and coverage without changing existing keys.

Welcome-bonus setup stores optional local spent amount, target, deadline, and reward label separately from issuer data and account balances. Plain decimal validation rejects malformed, negative, overflow, or scientific-notation amounts before expansion; targets must be positive, dates valid, and reward labels at most 120 characters. Fields identify and focus validation errors. A failed settings write keeps the previous state and shows visible feedback rather than claiming it saved.

Global Search

Search is placed with the top-right dashboard and Benefits actions, with no new bottom tab. Search separates Rewards and Benefits results and searches added programs, stored cards, and the benefits produced by the existing display model. Rewards result tiles show only the program image, name, and stored points. Benefits matches have independently collapsible program, card and canonical section groups with chevrons. Program headings use larger themed text with a small bundled program image; compact card headers show a small bundled card image, name, and ending and always open the exact card, with a separate right-side chevron for collapse. Single-line title-only benefit tiles retain canonical card-page order and open the full benefit tile. A program result scrolls to its exact Rewards tile with a temporary four-second outline. A program-only query such as Amex includes all of that added program's stored cards and canonical benefits. Mixed contextual queries combine an item's own text with program or card context and still require at least one own-text token; canonical source titles remain aliases. Query, selected result tab, group collapse choices, and per-tab scroll state stay in memory for the Search navigation entry. Exact source and revision checks precede result navigation; a benefit result temporarily reveals its category without changing saved collapse settings. Back preserves the originating viewport and the Search result position while their entries survive. Read and stale-selection failures use generic retry or reselect notices. See Global search for corpus boundaries, matching, and reveal validation.

Privacy Rules

  • Logs name programs and hosts only, never full URLs, page text, balances, cookies, passwords, or codes. DiagnosticLog also appends these lines to no_backup/diagnostics.log (capped at 512 KB), so a stop can be diagnosed after the phone's log buffer rotates; on a debug build, read it with adb shell run-as com.bendourthe.milestone cat no_backup/diagnostics.log.
  • An Amex card is identified on the phone by its last digits only; a Chase card by an opaque local id, its stored ending, and an HMAC-SHA256 binding of its selector option under a per-install key that is never backed up. Full card numbers, raw selector ids, account keys, and membership numbers are never stored, logged, or sent; the page script strips grouped digit runs, identifier-like tokens, and account-key-shaped runs before posting, and benefit reminders show only "A card benefit expires soon" on the lock screen.
  • Real captured pages live only in the gitignored app/src/test/resources/fixtures-private/; committed fixtures in app/src/test/resources/fixtures/ are hand-written with fake balances.
  • Cloud backup and device transfer exclude every app data domain (res/xml/backup_rules.xml, res/xml/data_extraction_rules.xml), and the vault sits in noBackupFilesDir, which Android never backs up.

Benefits Reader

The Amex sections below describe the American Express read; the Chase sections describe the Chase read (ADR-0009). The Amex benefits read starts after a saved American Express balance, in the same program profile. It reads cards and benefit sections from the site's existing controls. It never signs in, composes an account-key URL, or fetches account data from another service.

Readiness

The script scrolls to load lower sections. A shape is steady when tracker count, listed-link count, and page height stay unchanged for two seconds. A page with no trackers gets a longer empty settle.

  • Rewards requires an activity or view-all link, a reached bottom, and settled content. At its 15-second readiness cap, an available activity link is still followed, and so is a view-all link when trackers are on screen, since some Rewards pages keep growing and never reach their bottom. A missing lower section may wait up to the supplied page timeout, capped at 20 seconds.
  • Activity requires its own content: the Rewards activity link must be absent, and at least one tracker or listed link must exist. Rewards content under an activity address is never accepted as an activity read.
  • View-all requires listed content whose count differs from the page it was opened from, then bottom and settle checks. A capped empty list does not erase the previous list.

Before pressing a link, the script leaves a document-local handoff note. An in-place address change adopts that note; a full document load drops it. After pressing an activity link, the script waits for navigation or a bounded unreadable result instead of posting partial Rewards trackers.

Card Switching

The selected card must match the target, and its tracker fingerprint must be nonempty and different from the previous card's. The fingerprint stays inside the script and is never posted. An emptied tracker area is not proof that the new card has loaded.

The switch cap is 12 seconds. A settled empty tracker area with the right markers may become an empty read after that cap. Old trackers still on screen produce a mismatch, preserving the stored card rather than assigning another card's trackers to it.

Run Budget

One deadline covers the whole 120-second benefits read, with margins for script and app cleanup. Each page gets at most 20 seconds and cannot extend the shared deadline.

At a card's first page, the scheduler reserves 20 seconds for its possible second page and 20 seconds for every remaining first page, including the current one. If that time is unavailable, it cuts second pages for this and all later cards. If fewer than 10 seconds remain for another card to start, it leaves that card unread. These cuts preserve stored sections that were not reached.

The 20-second first-page reserve includes a late Rewards lower section. Reserving only 15 seconds could spend time on an earlier activity page and leave the last card unread.

Storing a Read

BenefitsCardReads records which sections a card's pages covered. Rewards alone covers tracker sections. A successful view-all adds the listed section. An activity page covers every section. A failed or mismatched view-all keeps the new trackers and the previous stored list.

Amex retitles a finished tracker "Congratulations!" and names the benefit only in its description ("You've earned a Free Night Reward"). Such a tracker is kept, checked as done, until it can be named: from the one listed benefit whose distinctive words its description contains, in the same read's list or the card's saved list, or else from the description's own "earned a ..." words when the card is saved. One whose description names nothing is dropped, as the yearly summary always was.

SyncManager sends those section sets to RoomCardRepository. The repository deletes and replaces only those sections in a transaction under the program lock. A failed card keeps its previous benefits. Cards disappear only when a complete card list no longer contains them.

Display and Freshness

Completed credit tiles render full progress with the earned/target ratio inline beside the bar. Their display-only target uses a positive stored target first, then a positive stored earned amount, then a single leading dollar amount in the completed credit title. A title with multiple dollar amounts or no usable leading amount supplies no inferred target. The display does not rewrite issuer amounts or stored rows. Unfinished credits retain actual progress and their inline ratio; noncredit trackers retain their existing amount labels. Enrolled appears beside every enrolled item's title, before the completed check when present. Enrollment required remains a body status.

Issuer sections remain the replacement boundary; display categories do not change stored rows. The card's successful-write generation increments inside the same Room transaction as section replacement. After that write, SyncManager records covered section generations in DataStore, bound to the exact Room generation and read time. If the outcome write is unavailable or cancelled, the UI labels list freshness unknown; equal timestamps cannot reuse an earlier generation. Tracker-only success preserves both old listed rows and their older source generation.

The presentation transform retains the original enrollment source when it merges a listed row into a tracker. Chase Path

The Chase read starts after a saved Chase balance and visits each Chase sign-in in its own WebView profile, within the shared 120-second deadline. A sign-in starts only with 20 seconds left, and a card only with 8 seconds left. The page script is re-entrant on every page of the path:

  • Dashboard: note how the home page groups the cards (under "Personal" or under a business name) and post only each ending with a true/false business flag, then press the first card entry, skipping forms, dialogs, and payment or transfer controls.
  • Card page: press More, then "Card benefits" in the menu sheet that opens in place. Labels are matched against the element's own text and its label attributes, and a component is pressed through the button inside its shadow root. A step waits for a visible change, including more visible controls for the next step, for up to 15 seconds (25 seconds for the Benefits page itself). A missing control (noControl) or no change (navigation) before the card list restarts the path once from the dashboard; a second failure ends the sign-in as unreadable with no card list, with count-only diagnostics.
  • Benefits: open the card selector, post the listed cards (name, ending, and which one is selected) once the list has stayed unchanged for 2 seconds, then read the selected card's benefit groups, rows (title, tag, value), and welcome tracker.

For the next card, the app sends the target option and the script presses it in the selector, at most once every 1.5 seconds, and waits for the page to change before reading. A handoff note survives single-page route changes. The script stops on any code, phone, or number field or a radio outside the selector (an identity check) and never chooses a delivery option. A page that keeps reloading stops the sign-in: the limit is 8 page loads plus 2 per listed card, so a site that reloads per card still finishes. After the card list, that stop is a budget stop, and unread cards keep their stored benefits; later sign-ins still start while the shared deadline allows. A card page with more than 30 groups, 150 rows, or 20 trackers is reported unreadable (overflow) and keeps its stored benefits instead of being stored partially.

Chase states how much of a credit is used only on the credit's own page. For each row in a list whose test id contains "Credit", with an amount and no Redeemed, Locked, Activate, or Enroll tag, the script presses the row, reads the page's gauge ("$X/$Y", its fill percentage, and its status line), and goes back, at most 8 credits per card and only while time remains to read the list. Only the row is pressed, never a control on the credit's page. A credit page with no gauge adds nothing. The card's log line counts the credit pages planned and the ones that gave a used amount.

ChaseBenefitsReader turns rows into listed benefits and the tracker into a spend tracker, taking amounts, periods, and status only from stated text. A row with a used amount becomes a credit with its earned, remaining, and total amounts. A tracker's title comes from its tile heading. A tracker's earned amount comes from "$X of $Y" wording or from a progress bar whose maximum is the stated target; "Earn $300 after you spend $3,000" is a reward and a target, not progress. Half-year wording such as "every six months" is read before monthly wording. A row value made of several parts is joined with " - ". Oversized or malformed payloads are rejected.

Chase Sign-ins and Coverage

The first Chase sign-in uses the program's own profile and owns the Rewards balance. Up to three more sign-ins (chase_2 and up) each get an isolated profile and never write a balance; a phone that cannot isolate profiles refuses them. Each sign-in is Personal or Business, chosen when it is added from the Chase sign-ins sheet. A card's section follows, first match wins, the owner's Show under choice, a business product name, the CardProducts list, the home-page group recorded by the read (applied only to an ending that appears once in both lists), and finally the sign-ins that reach it.

Cards are bound by an HMAC-SHA256 of their selector option under a per-install key in noBackupFilesDir; the stored card gets an opaque c_ id. Each sign-in's card list updates only its own coverage rows. Only a complete list removes coverage, and a card is deleted only when no sign-in reaches it. Partial, empty, stale, duplicate, or unknown lists change nothing, and so does a complete list that shares no card with the sign-in's existing coverage: that looks like the selector's ids changing, and applying it would delete every card with its benefits, preferences, and reminder history. Removing Chase signs out every additional sign-in before its records are deleted. A card's segment is Personal when a Personal sign-in reaches it, otherwise Business; the user's choice from the card page's Show under menu wins and survives refreshes. A card already read through an earlier sign-in is not read again in the same refresh.

Read Deadline

The complete benefits read shares one 120-second deadline.

  • A page gets at most 20 seconds within the remaining budget.
  • Reserve the full first-page maximum before allowing a second page.
  • Cut second pages before leaving later cards unread; once cut, later second pages stay cut.

Run Budget

One deadline covers the whole 120-second benefits read, with margins for script and app cleanup. Each page gets at most 20 seconds and cannot extend the shared deadline.

At a card's first page, the scheduler reserves 20 seconds for its possible second page and 20 seconds for every remaining first page, including the current one. If that time is unavailable, it cuts second pages for this and all later cards. If fewer than 10 seconds remain for another card to start, it leaves that card unread. These cuts preserve stored sections that were not reached.

The 20-second first-page reserve includes a late Rewards lower section. Reserving only 15 seconds could spend time on an earlier activity page and leave the last card unread.

Unit tests can prove matching and stale-target rejection, while emulator interaction must confirm the right-side icon, counted result tabs, grouped compact matches, canonical benefit order, exact card-header navigation and independent chevrons, program-only child matching, exact full-tile destination, category reveal, visible updating states, Clear, keyboard, Back, and per-tab scrolling. The platform profile keeps the debug functional suite and runs the performance scenario in a non-debuggable, R8-optimized benchmark app through an independent test controller. The debug latency test remains an optional diagnostic; both adapters share one scenario. The performance fixture uses stored synthetic data for 25 added programs, 100 cards and 2,000 displayed benefits. It measures 30 queries after three warmups using normal Android frames, the production result content and its animated background. The interval starts at the query update and ends at a draw containing the expected current result inside the list viewport; an exact clickable title is checked after each populated sample. Empty queries must draw the matching Empty state, with the same current-query, generation and foreground checks. The p95 (95th percentile) limit is 200 ms. Initial reading, the keyboard and initial focus are excluded. The declared fixture viewport remains 1080x2340 pixels.

The host hashes the candidate target and controller APKs, and the controller independently verifies both installed APKs before starting the fixture. A signature-protected completion signal and fresh UUID bind the exported synthetic metrics to this run; export collection happens after measurement. Missing, partial, stale, mismatched or nonfinite metrics, a changed workload, a dishonest p95 summary, skipped runtime cases or a failed task cannot qualify the profile. The host recomputes p95 from all 30 observations and attempts each owned-package and UUID-output cleanup even if an earlier cleanup operation fails. The benchmark uses a separate package, empty Application and disabled production entry points, so it does not initialize issuer sessions or background refresh work.

Application release and runtime qualification remain separate from this handbook's reproducible build and browser checks.
