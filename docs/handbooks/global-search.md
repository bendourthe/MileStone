# Global Search

Global search is part of the local v0.4.0 candidate. The installed version metadata remains v0.3.1, version code 4; this candidate has not been released. A top-right Search icon sits with the dashboard and Benefits actions and opens a separate navigation entry. Search has Rewards and Benefits result tabs; the existing bottom navigation remains unchanged, with no Search tab. Search uses stored items without signing in, refreshing an account, or making a remote search request.

## Stored Corpus

`SearchViewModel` builds a snapshot from added accounts, their stored cards and benefits, and per-card display preferences. Cards and benefits are read together through the repository's Room transaction. Programs absent from the user's added accounts are excluded. The snapshot uses `BenefitsViewModel.page` and `BenefitsPresentation.presented`, so benefit results follow the destination's displayed rows and conservative duplicate owner. Source titles retained during canonical merging remain search aliases for that displayed benefit; they do not create duplicate results.

`SearchViewModel` prepares tab partitions, counts, and card groups on its worker dispatcher; the screen reuses those cached projections.

Program names, program identifiers and categories, card names, benefit titles, descriptions, and canonical source-title aliases contribute to matching. Card digits are removed from the matching text. Each compact Benefits card header shows a small bundled card image, name, and ending; freshness remains nonvisual accessibility context outside the matcher. Current monetary values and other internal identifiers are not corpus fields. Rewards result tiles show the program image, name, and stored points only; those stored points do not become a matching field. Compact benefit tiles show a single-line title without details. Stored completion, period and enrollment remain available on the full destination and do not become extra matching fields. Collapsed categories remain searchable because collapse affects visibility rather than membership in the displayed page model.

## Contextual Matching

The query is limited to 256 characters. Matching applies simple Unicode case folding per code point, turns non-letter and non-number separators into spaces, and matches normalized tokens as substrings. The same fold locates context excerpts, including symmetric matches for sigma variants, long s, and the micro sign. When every normalized token matches a program's name or identifier, that program-only query includes all of its stored cards and canonical displayed benefits. For example, `Amex` includes the added Amex program's stored children without requiring an item token. Mixed contextual queries still require every token to appear in the item's own text or program/card context and at least one token in the item's own title, description, or aliases. Card parent context includes the program identity; benefit parent context also includes the card name. Blank normalized input shows the start prompt rather than all items.

The counted Rewards tab contains matching programs. The counted Benefits tab groups matching cards and compact benefit matches under their program and card headers. Benefit matches retain the category and item order from that card's canonical Benefits page, including its saved sort and Completed last settings. Programs, cards and canonical benefit sections have independent chevron collapse controls, initially expanded. Program headings use a larger title, a distinct theme color, and a small bundled program image, including for benefit-only queries. Compact card headers show a small bundled card image beside the name and ending, without visible freshness detail or a bright outline. Selecting the card header opens its exact card; a separate right-side chevron only expands or collapses its matches. Compact benefit tiles show the matching title on one line with ellipsis for overflow, without details; description and alternate-title matches still lead to the exact full tile. The full benefit remains available at the destination. Without an explicit tab choice, program matches select Rewards; card or benefit matches without program matches select Benefits. Search does not rewrite saved dashboard or card display sorting.

## Selection Validation

Each snapshot has an opaque, memory-only revision. Selecting a result requires a fresh repository read, unique target membership, equality with the expected source snapshot, and the same observed revision. Stable keys alone cannot authorize opening an item after stored rows or display preferences change. A monotonic query-edit version rejects a delayed selection if the query was edited, even when the text changes back to its original value. The card destination also checks its exact card, ordered benefit rows, and preferences against the snapshot. Benefit reveal validates again after the category layout is ready, before scrolling.

A program result opens the dashboard, scrolls to that exact program and adds a temporary four-second outline. Every card header opens its exact card detail, including a header supplied as context for benefit matches. Its separate chevron changes only the group's expanded state. A compact benefit match opens the full benefit tile on its exact card detail. The existing reveal temporarily expands its category, scrolls to the row, highlights it, and announces its title for accessibility. This temporary expansion does not save a new collapse preference. Explicit Hide dismisses the visit-local expansion so the category can close normally. A missing item, changed source, read failure, or reveal timeout returns a generic notice instead of selecting a nearby row or silently falling back to another card.

## Navigation and Privacy

Query text, the selected result tab, per-tab scroll positions, group collapse choices, and reveal state belong only to the Search navigation entry's ViewModel in memory. They are not persisted as history, route arguments, or saved instance state. Returning from a result preserves this state while that entry survives; Back from Search returns to the prior screen. The outgoing screen retains its viewport when the bottom bar is hidden, including an end-of-list position. An actual query edit resets both result list positions, group collapse choices, and the explicit tab choice, and Clear empties the query and focuses the field.

Source errors show a retry action. Selection errors use the generic messages "Results changed. Select the item again", "That stored item is no longer available", or "Stored items could not be read. Please retry". Query text is not added to diagnostics, analytics, notifications, or account refresh requests. Search uses stored data; selecting a match does not imply a fresh remote read. Card freshness remains available to accessibility services and on the full destination.

## Verification

The matcher, snapshot and revision logic, navigation, temporary reveal, and screen behavior need separate checks. Unit tests can prove matching and stale-target rejection, while emulator interaction must confirm the right-side icon, counted result tabs, grouped compact matches, canonical benefit order, exact card-header navigation and independent chevrons, program-only child matching, exact full-tile destination, category reveal, Clear, keyboard, Back, and per-tab scrolling. The local v0.4 candidate's release and independent UI qualification remain separate from this handbook's reproducible build and browser checks.
