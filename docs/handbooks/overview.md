# Repository Overview

MileStone is a native Android app (`com.bendourthe.milestone`) that shows the points, miles, and rewards cash of the user's loyalty programs on one dashboard, and, for American Express and Chase, each card's benefits on a Benefits tab. It reads each balance from the program's own website inside an embedded browser (Android WebView) after the user signs in once, and keeps those sign-ins alive in the background. Account balances are read automatically; optional welcome-bonus spending is entered locally. No server is involved: every balance, sign-in, and saved password stays on the phone.

The remote `origin` is `https://github.com/bendourthe/MileStone.git`. `main` is the release branch and `develop` is the integration branch. The version is the latest heading in the root `CHANGELOG.md`.

## Toolchain

- Kotlin, Jetpack Compose (Material 3), Gradle with a version catalog (`gradle/libs.versions.toml`).
- `compileSdk` 37, `targetSdk` 36, `minSdk` 29.
- Build types: `debug`, `release`, and `capture`. `capture` is a debug copy with the suffix `.capture` and the label "MileStone Capture"; it adds a "Capture page" action that saves a page for selector work. Captures are copied to the PC through `app/src/capture/sanitize_capture.py`, which strips identifiers on the way, and inspected only through `inspect_capture.py`, which prints structure with text masked. CI never builds it ([ADR-0001](../decisions/0001-login-bridge-sessions-fixtures-logging.md)).
- The `debug` build adds a "Site check" launcher entry (`app/src/debug`) for testing whether a program's site works in the embedded browser.

The canonical validation entrypoint is `scripts/validate.py`. The `fast` profile checks the private-input boundary, Python and extractor syntax, and handbook freshness. The `full` profile adds validation-helper tests, unit tests, lint, debug and local capture builds, instrumented-test compilation, coverage, Room schema checks, handbook browser checks, and secret scanning. Full validation needs the Playwright dependency in `scripts/requirements-validation.txt` and its Chromium browser, plus installed Gitleaks or the documented preloaded Docker image; the profile does not install those tools.

Local full gate, run from the repository root in PowerShell:

```powershell
python scripts/validate.py --profile full --quiet
```

Use `python scripts/validate.py --profile fast --quiet` for the smaller checks. `--list --json` lists a profile's commands without running them or writing reports. Profiles write results under `reports/` by default; `python scripts/validate.py --profile report --quiet` aggregates existing receipts without rerunning checks. The collector preserves JUnit exports and rejects reported failures or errors even if Gradle returns zero; the platform profile requires JUnit cases from both its debug functional task and its optimized Search task, rejects skipped runtime cases, and ignores unrelated variant reports. The `release` profile packages a clean committed source archive, verifies reproducible archive bytes and safe paths, and records version, commit, and SHA-256 metadata. It does not build an APK, use signing secrets, rerun tests, publish, or tag a release; debug sideloads remain separate.

The local emulator runtime gate is separate from `full`:

```powershell
python scripts/validate.py --profile platform --quiet
```

This profile accepts only `emulator-5554`, verifies `ro.kernel.qemu` is `1`, and sets each test child's `ANDROID_SERIAL` to that emulator. It runs the debug functional suite with only the optional debug latency diagnostic excluded, then measures the shared Search scenario through `searchBenchmark` against a non-debuggable, R8-optimized `benchmark` app. The 30 samples, three warmups, real visible-draw endpoint, animated background and 200 ms p95 limit remain unchanged. Both tasks and their JUnit evidence must pass. Benchmark artifact metadata also binds the measured run to its parent validation invocation. A failed native runtime step can trigger one separate scheduler/frame diagnostic only when current invocation, source, APK and completed latency-failure evidence match. Missing or malformed evidence skips collection. Diagnostic output never qualifies the original failed gate; native cleanup failures or an unfinished trace worker keep the diagnostic failed and report cleanup uncertainty. The native profile retains fresh UUID-correlated metrics in `reports/metadata/search-latency.json` and expected APK hashes in `search-benchmark-artifacts.json`; the controller checks the installed target and controller hashes before measuring. Do not run connected tests against the owner's phone: installing the test app clears its sign-ins. Instrumented-test compilation in `full` is not runtime proof.

CI (`.github/workflows/ci.yml`) is configured to validate pull requests to `develop` or `main` on Ubuntu 24.04 with Java 17. After preparing the pinned dependencies, it runs `.validation-venv/bin/python scripts/validate.py --profile full --platform ci-linux --quiet`, installs the Android 36 Google APIs x86_64 image, verifies KVM acceleration, boots an isolated headless `emulator-5554`, and runs `.validation-venv/bin/python scripts/validate.py --profile platform --platform ci-linux --quiet`. Emulator cleanup, report aggregation, and report upload are configured to run even after failure. `CI result` requires the validation job to succeed for those target branches. The explicit `ci-linux` full profile still excludes the local-only capture build under [ADR-0001](../decisions/0001-login-bridge-sessions-fixtures-logging.md).

## Module Layout

Production code is in the `app` module under `com.bendourthe.milestone`. The test-only `searchBenchmark` module runs its own instrumentation process so normal release shrinking does not remove APIs that its runner expects. `app/src/searchScenario/` holds one synthetic scenario shared by the debug diagnostic and optimized fixture. `app/src/benchmark/` supplies a signature-protected, emulator-only activity in a separate `.benchmark` package, with an empty Application and disabled production entry points. These fixtures are absent from the normal debug, capture and release app APKs; they use an in-memory database and private scratch preferences rather than issuer sessions.

| Package | Responsibility |
|---|---|
| `domain` | Models (`Program`, `ExtractionSpec`, `BenefitsSpec`, `SyncResult`, `FailureReason`, `BalanceUnit`), card and benefit models with stable keys (`Benefits.kt`: a card is its program plus a local card id, which for Amex cards is their last digits and for Chase cards an opaque `c_` id; a benefit is its card plus title or the issuer's list key plus period), issuer sign-ins and card coverage (`Connections.kt`), `BenefitPeriods` (period labels to end dates), repository interfaces, catalog search, and the dashboard use case. No Android types. |
| `data.catalog` | `StaticCatalogRepository`: the 14 programs, their hosts, sign-in and balance URLs, and fixture-verified XPath or CSS balance selectors, and the benefits pages and selectors for American Express (`AMEX_BENEFITS`, [ADR-0008](../decisions/0008-amex-benefits-card-navigation.md)) and Chase (`CHASE_BENEFITS`, [ADR-0009](../decisions/0009-chase-benefits.md)). Hosts come only from the feasibility record. |
| `data.db` | Room database version 5 (`loyalty_accounts`, `balance_snapshots`, `cards`, `issuer_connections`, `card_coverage`, `benefits`, `benefit_reminders`; cards, sign-ins, coverage, benefits, and reminder records cascade from their account, sign-in, or card), `RoomCardRepository`, schema exports in `app/schemas/`. The version 4 to 5 migration keeps every Amex card, benefit, and reminder under its existing key. |
| `data.session` | `TinkSessionStore`: encrypted per-program session metadata (connected and verified times), never cookies. |
| `data.credentials` | `CredentialVault`: saved sign-ins sealed with AES-256-GCM under an Android Keystore key (StrongBox when available), one file per program in `noBackupFilesDir/signins` ([ADR-0004](../decisions/0004-keep-alive-and-automatic-sign-in.md)). |
| `data.settings` | DataStore preferences for dashboard sorting and card-specific benefit sorting, collapsed categories, alert acknowledgements, optional welcome-bonus setup, and section-read outcomes. |
| `sync` | `SyncManager`, the single writer of balances and statuses, with per-program throttle, backoff, and refresh reasons (`ON_START`, `MANUAL`, `KEEP_ALIVE`); `ForegroundSyncObserver` refreshes when the app opens. |
| `sync.webview` | The login bridge: `WebViewConfig` (hardened settings and a full-height layout, without which Chromium lays pages out with a zero viewport height and every `vh` length is 0), `HostPolicy` (exact-host allow list), `SessionProfiles` (one WebView profile and cookie store per program), `BridgeSession` (the page-state machine), `LoginBridge` (WebView glue), `HeadlessWebViewBalanceSource` (refresh without UI), `HeadlessWebViewBenefitsSource` (the Amex benefits read, card by card), `ChaseBenefitsSource` (the Chase read, sign-in by sign-in), `ConnectionSessions` (extra issuer sign-ins, each in its own profile), and `AutoSignInSupport`. |
| `sync.extract` | `BridgeProtocol` (messages to and from the page script, with benefits messages accepted only from the catalog's benefits pages), `BenefitsReader` and `ChaseBenefitsReader` (field checks, caps, and section rules), `BindingHasher` (Chase card bindings), `BenefitAmountParser`, `PageStateClassifier`, and `BalanceParser`. |
| `sync.mfa` | `OneTimeCodeInbox` and `SmsCodeReceiver`: texted sign-in codes held in memory for five minutes, matched by sender keywords, handed out once. |
| `sync.background` | `KeepAliveScheduler`, `KeepAliveReceiver`, and `KeepAliveService` (a refresh every 15 minutes as a short `dataSync` foreground task), `ScheduledRefreshScheduler` (an alarm at the next scheduled midnight, allowed while the phone idles), `VirtualDisplayWebViewHost` (an off-screen WebView), `BenefitReminders` (the daily credit reminder check, its private notifications, and its 9:00 alarm), and the notification channels. |
| `ui` | `MainActivity`, the navigation host (Rewards, Benefits, Settings), the dashboard, the Benefits tab and card pages (`ui.benefits`), the program catalog, settings, and the sign-in sheet (`AuthWebViewModal`, `AutoSignInDialog`). `ui.theme` holds the single dark teal color scheme and `AuroraBackground`, a slow animated gradient drawn in its own graphics layer behind the foreground. Its dark teal gradient and three drifting glows share a minute-long loop and stay still when system animations are off. |

The aurora rasterizes its base gradient and three glows into a high-precision image owned by each background, with a longest side of at most 256 pixels, then scales that opaque image across the background in one draw. It reuses the image while the phase stays unchanged, updates it at the current continuous phase, and replaces it when its raster dimensions change. The original glow positions, radii and minute-long motion remain unchanged. The native rendering regression compares the output with the original separate-gradient reference across phases, viewports including 1080x2340, and color buffer formats; this color comparison does not qualify Search timing.

`AppContainer` wires these together by hand; there is no dependency-injection framework.

## Runtime Flow

1. The user adds a program from the catalog and signs in inside `AuthWebViewModal`. The page script `app/src/main/assets/extract.js` runs only on the program's exact hosts, reads the balance element named by the catalog selector, and posts it back; `SyncManager` stores it.
2. `SyncManager` refreshes programs in a hidden WebView that reuses the program's own cookie store. The user's schedule in Settings (every day, every Sunday by default, or the last day of the month, each at midnight) sets an alarm that refreshes every balance older than that time and may sign in. Opening the app refreshes a program only when it was neither updated nor tried since that scheduled time; a failed program waits for the next scheduled time or the user's Refresh. Every 15 minutes in the background, the keep-alive reads connected programs to keep their sessions alive. Reads share two fetch slots and sign-ins run one at a time; a sign-in the user just started skips that queue.
3. When a session has ended and the user saved an automatic sign-in, the hidden browser opens the program's sign-in page directly (and skips the session read when the last one already found the session ended), and the page script fills the saved username and password, ticks "remember this device", prefers a texted code, and enters a code that arrives by text. A site that asks for the username alone first gets the username, then at most one more fill on its password page. The script submits with the form's Sign in or Continue button and never presses a show-password toggle. A successful password submission starts the existing page window again so a delayed saved-password fill still allows the existing second press; retry counts and the overall 180-second sign-in limit are unchanged. Passwords are typed when the user opens MileStone or at the scheduled refresh, never by the 15-minute keep-alive ([ADR-0005](../decisions/0005-sign-in-only-on-open-with-stop-reasons.md)). A sign-in counts as refused only when the site shows an error with its form; a form back without an error is unfinished and may be tried again. A refused password is never retried: automatic sign-in pauses for that program until the user taps Sign in or Refresh on its tile, which tries the saved sign-in once more and opens the site for the user if it stops again, or until a sign-in succeeds. A background refresh that needs the user posts a "needs you" notification.
4. Signing out or removing a program cancels its running refresh or sign-in, erases its WebView profile's cookies and storage at once, and deletes its saved sign-in; removing a program also signs out each of its additional sign-ins; a profile still held by a live WebView is deleted at the next app start.
5. After a saved American Express balance (not for the keep-alive), a separate benefits read opens the Amex Rewards page in the same profile. The page script reports the card switcher's cards (names and last digits only), then presses the switcher option for each next card and follows the page's own activity link for cards that have one. Cards without an activity page post their Rewards trackers before opening their own view-all link for the full list. Each page waits for its own content markers, scrolling to load lower sections and checking that counts and height have settled; after a switch, the new card's trackers must replace the previous card's. At the 15 s Rewards readiness cap, an available activity link is followed even while the page is still growing; a missing lower section can wait up to the app's page timeout, at most 20 s. One deadline bounds the whole benefits read to 120 s, cutting second pages before leaving cards unread when time is short. The read never signs in and never reads an account key ([ADR-0008](../decisions/0008-amex-benefits-card-navigation.md)). `SyncManager` replaces only the sections actually read: a failed view-all page keeps the previous list, and an unread card keeps its previous benefits. A card is removed only when a complete card list no longer shows it. Count-only diagnostics identify page kind, readiness, wait time, card index, and total read time. The Benefits tab groups cards by program with matching offline artwork, benefit counts, yellow alert counts, next open credit, and freshness. The card display and acknowledgement rules are described below.
6. After a saved Chase balance, the Chase benefits read visits each Chase sign-in in its own profile within the same 120 s budget ([ADR-0009](../decisions/0009-chase-benefits.md)). The page script follows the owner's path (a card on the dashboard, More, Benefits), lists the cards in the Benefits card selector, and reads each card's benefit groups, rows, and welcome tracker, pressing the selector for the next card. It stops without choosing anything on an identity check, never presses a payment control, and never signs in. A card already read through an earlier sign-in is skipped. A card's identity is an HMAC-SHA256 of its selector option under a key kept in `noBackupFilesDir`, so the raw option id is never stored; the stored card gets an opaque local id. `SyncManager` applies each sign-in's card list (only a complete list can remove a card, and only from that sign-in's coverage; a complete list that shares no card with the sign-in's coverage changes nothing) and the benefits read per card. A card whose page has more rows, groups, or trackers than the read may post is left unread rather than stored partially. A card read stopped by the deadline or a page limit keeps its stored benefits, and the read is reported as stopped. The page limit grows with the number of listed cards, so a site that reloads the page per card still finishes.
7. Once a day at 9:00 and when the app opens, the reminder check posts one private notification per statement credit and period when part of the credit is unused and its period ends within 7 days (monthly), 14 (quarterly), or 30 (half-year and yearly), never from benefits read more than 8 days ago and never twice for the same credit and period. Settings has a Benefit reminders switch, on by default.
8. Add program opens on programs not added yet, with a filter for Added and All programs; added programs carry a green outline. Programs whose sites do not work in the embedded browser cannot be added, and tapping one says so. Pulling the dashboard down asks "Refresh all programs?" before refreshing everything, since a full refresh can take minutes; the top refresh button refreshes at once. An added program's menu offers Refresh, Sign out, and Remove; "Open in app or browser" was removed ([ADR-0002](../decisions/0002-open-in-app-or-browser.md), [ADR-0003](../decisions/0003-sync-only-catalog-and-reconnect.md), [ADR-0007](../decisions/0007-catalog-filter-and-added-outline.md)).

## Benefits Display

Benefits starts with one tile per tracked institution that supports card benefits, with card and active-alert counts. Pressing an institution opens only its cards; card Back returns to that card list and list Back returns to the institutions. Connected institutions remain visible before their cards are read. Tapping a supported program on Rewards opens its card list directly; reminders open the named card with the same parent hierarchy. Known Platinum, Business Platinum, Hilton Surpass, and Delta Gold products use distinct bundled public artwork; an unknown product uses a generic offline card icon. Each card page groups Welcome bonus, Credits, Spend trackers, and Other. The top-right sort menu offers Name A-Z (the default), Name Z-A, Deadline soonest, and Largest amount remaining within each category, with unknown dates or amounts last. The separate top-right filter menu holds Completed last, applied before the selected sort. Both choices are saved per card. Outlined, counted category headings have explicit Show/Hide controls and collapse independently, with Other initially collapsed. Completed items retain their category with a check and strike-through; an unknown completed kind remains in Other rather than being inferred from its amount. Completed credits show a full progress bar. The display uses a positive stored target, then a single explicit leading dollar amount in the completed credit title, to show the completed target/target ratio beside the bar. An earned amount alone never establishes a target; when no target is known, the actual earned label remains beside the full bar. Unknown or multiple dollar amounts are not inferred. This display-only fallback does not change stored issuer rows. Unfinished credits retain actual progress and the inline ratio; other trackers keep their existing amount labels. Enrolled appears beside the title before the completed check, while Enrollment required remains in the body.

Chase appears as two institution tiles, Chase Personal and Chase Business. A Chase card is Personal when any sign-in declared Personal reaches it, otherwise Business; the card page's top-right Show under menu moves one card to the other tile, and that choice survives refreshes. Chase Personal always shows; Chase Business shows once a card belongs to it. A card with no segment yet stays visible under Personal with "Needs Personal or Business". Each Chase card page lists the Chase sign-ins: each can be declared Personal or Business, another isolated sign-in can be added (up to four, refused with an explanation when the phone cannot keep separate profiles), and an extra sign-in can be signed out, which removes only the cards that no other sign-in reaches. The first sign-in owns the Chase Rewards balance; extra sign-ins never write a balance. Card tiles, Search results, and reminders show the stored card ending and open the exact card by its local id, so two cards with the same ending stay distinct.

The local welcome-bonus form groups amount digits with commas while preserving exact cents and cursor positions. Saved whole-dollar values reopen without .00; fractional cents remain precise. Standalone numbers in the Reward field and local reward description also group with commas, while raw free text, codes and dates remain unchanged. The optional deadline displays YYYY-MM-DD separators during entry and accepts a calendar selection. Choosing a calendar date changes the draft only; Save commits the setup. Calendar dates are converted in UTC so the selected calendar day stays unchanged across time zones. Invalid amounts or dates show field-specific errors.

A listed entry merges into a tracker only when the same-card title/period match is unambiguous and enrollment statuses do not conflict. Description and enrollment details remain visible on the copied tracker. Raw issuer rows stay stored for refresh, reminders, and count verification. Different periods or ambiguous matches remain separate.

Yellow alerts appear above the card artwork and categories. They identify enrollment requirements, unused credits near their established reminder deadline, stale reads, and a listed-benefits section that failed to refresh. Acknowledge hides one alert and updates its count without changing enrollment, issuer rows, or notification records. Acknowledgements survive navigation and restart. Only a successful relevant section read can reintroduce a still-applicable source alert; tracker period changes do not change a retained listed enrollment's identity. Failed or cancelled reads cannot reset it. Local welcome-bonus deadline alerts instead follow the saved manual setup.

Each successful section replacement increments the card's Room read generation in the same transaction. The following DataStore outcome binds to that generation and read time and advances only the sections actually covered. A mismatch or unavailable outcome is labeled unknown; an older list is explicitly identified when only trackers refreshed. A whole-card timestamp alone never proves list freshness. The additive version 3 to 4 migration preserves accounts, benefits, enrollment, and reminder records; the version 4 to 5 migration adds sign-ins and coverage without changing existing keys.

Welcome-bonus setup stores optional local spent amount, target, deadline, and reward label separately from issuer data and account balances. Plain decimal validation rejects malformed, negative, overflow, or scientific-notation amounts before expansion; targets must be positive, dates valid, and reward labels at most 120 characters. Fields identify and focus validation errors. A failed settings write keeps the previous state and shows visible feedback rather than claiming it saved.

## Global Search

Search is placed with the top-right dashboard and Benefits actions, with no new bottom tab. Search separates Rewards and Benefits results and searches added programs, stored cards, and the benefits produced by the existing display model. Rewards result tiles show only the program image, name, and stored points. Benefits matches have independently collapsible program, card and canonical section groups with chevrons. Program headings use larger themed text with a small bundled program image; compact card headers show a small bundled card image, name, and ending and always open the exact card, with a separate right-side chevron for collapse. Single-line title-only benefit tiles retain canonical card-page order and open the full benefit tile. A program result scrolls to its exact Rewards tile with a temporary four-second outline. A program-only query such as `Amex` includes all of that added program's stored cards and canonical benefits. Mixed contextual queries combine an item's own text with program or card context and still require at least one own-text token; canonical source titles remain aliases. Query, selected result tab, group collapse choices, and per-tab scroll state stay in memory for the Search navigation entry. Exact source and revision checks precede result navigation; a benefit result temporarily reveals its category without changing saved collapse settings. Back preserves the originating viewport and the Search result position while their entries survive. Read and stale-selection failures use generic retry or reselect notices. See [Global search](global-search.md) for corpus boundaries, matching, and reveal validation.

## Privacy Rules

- Logs name programs and hosts only, never full URLs, page text, balances, cookies, passwords, or codes. `DiagnosticLog` also appends these lines to `no_backup/diagnostics.log` (capped at 512 KB), so a stop can be diagnosed after the phone's log buffer rotates; on a debug build, read it with `adb shell run-as com.bendourthe.milestone cat no_backup/diagnostics.log`.
- An Amex card is identified on the phone by its last digits only; a Chase card by an opaque local id, its stored ending, and an HMAC-SHA256 binding of its selector option under a per-install key that is never backed up. Full card numbers, raw selector ids, account keys, and membership numbers are never stored, logged, or sent; the page script strips grouped digit runs, identifier-like tokens, and account-key-shaped runs before posting, and benefit reminders show only "A card benefit expires soon" on the lock screen.
- Real captured pages live only in the gitignored `app/src/test/resources/fixtures-private/`; committed fixtures in `app/src/test/resources/fixtures/` are hand-written with fake balances.
- Cloud backup and device transfer exclude every app data domain (`res/xml/backup_rules.xml`, `res/xml/data_extraction_rules.xml`), and the vault sits in `noBackupFilesDir`, which Android never backs up.

## Tests

- Unit tests (`app/src/test`, Robolectric where Android types are needed) cover the catalog, Room and its migrations, cards and benefits storage, the vault, the code inbox, the bridge state machine and benefits protocol, `SyncManager` with its benefits read, period labels and reminders, the Benefits screens, and `ExtractorFixtureTest` and `BenefitsFixtureTest`, which run every selector against its synthetic fixture and, locally, its private capture. Chase coverage, sign-ins, identity, tiles, the reader, and the version 5 migration have their own tests (`ConnectionCoverageTest`, `ConnectionSessionsTest`, `ChaseIdentityTest`, `ChaseBenefitsTilesTest`, `ChaseBenefitsReaderTest`, `ChaseSyncApplyTest`, `MigrationTest`); `ChaseCaptureFixtureTest` counts rows on the private Chase captures without printing them.
- Instrumented tests (`app/src/androidTest`) cover WebView configuration, headless sync and the Amex and Chase benefits reads against local fixtures (with identifier decoys, payment and identity-check controls, a ten-card account that reloads per card, a selector that lists cards in batches, and an over-cap card), a reminder notification, and screenshots of the Benefits screens. Running them uninstalls the app, which clears every sign-in and saved password.

The [benefits reader](benefits-reader.md) companion describes Amex page readiness, card switching, time limits, and section-scoped storage, and the Chase path, sign-ins, and card coverage, in more detail. All three sources are included in the [offline handbook](html/overview.html).
